# Plugin system

Plugins extend the desktop agent. One manifest — `open-bot.plugin.json` — describes everything; GitHub repos hold the code and releases; the [marketplace](/docs/marketplace) is the searchable index.

## Manifest

Schema: `packages/plugin-kit/schema/open-bot.plugin.schema.json` (seeded into desktops and referenced by `ob-plugin new` scaffolds; kept in sync with `validatePluginManifest`).

Key fields:

| Field | Purpose |
| --- | --- |
| `files[]` | `{name, source, exec}` payload files fetched from the reviewed release tarball at install; text files only. |
| `setup.commands` / `setup.uninstall` | Root commands run at install (and after every desktop recreate via `onDesktopReady` → `reapplyPluginSetup`; the update recycle waits for that re-run to finish); uninstall runs best-effort. Logged to `~/.open-bot/plugin-init/<id>.log`; shown in the consent dialog; security-reviewed. Must be **idempotent** — they re-run on an already-set-up desktop, so every step has to succeed twice (pipe `grep`/`diff` style exits through `\|\| true`, guard installs with `test`). |
| `opencode.agents` | Registers new agent workers (deep-merged into `opencode.json`; reserved names rejected). Helper sessions must use the `worker:` title prefix so the dashboard hides them. |
| `opencode.agentTools` | Patches tool globs on existing agents, e.g. `{"build": {"blender_*": false}}`. |
| `opencode.agentsMd` | Standing instructions injected next to AGENTS.md (file under `~/.config/open-bot/agents-md/`). |
| `configs[]` | Typed settings: `string` (default), `bool`, `number`, `enum` + `options[]`, `secret`. Validated/coerced by `validateConfigValue`; unknown keys rejected; upgrades prune dropped keys. Secrets land in `~/.config/open-bot/plugin-<id>.json`. |
| `hooks[]` | Max 8 `{event: "session.idle"\|"thread.created", message}` prompts run in hidden `worker: plugin-<id> <event>` sessions. Loop-guarded: worker/cron sessions never re-trigger; **20 runs/day per plugin**; **2 concurrent per event**. |
| `permissions.notifications` | `true` unlocks `ob-plugin notify` → `POST /api/plugins/notice` (30/hour) → dashboard toast + native notification. |
| `pricing` | `{model: "one-time", amount: <USD cents>}` ($0.99–$500) makes it a premium listing — see [Marketplace](/docs/marketplace#paid-plugins). |
| `version` | Semver `X.Y.Z[-prerelease]` or dev tag (`beta-1`). |

## Config guide (CONFIG.md)

Every plugin project ships a repo-root `CONFIG.md` — the configuration guide the **installing** agent reads when it configures the plugin with the user. `ob-plugin new` scaffolds a template; fill it in whenever the manifest declares `configs[]` or vault slugs (`ob-plugin doctor` warns when it is missing or still the placeholder).

What goes in it: what the plugin needs configured, each setting and what to ask the user, each `vaultCreate` slug and where the user gets the key, the ask → fill → verify order (using `ob-plugin settings` / `ob-plugin vault` — never echo secret values), and how to verify the plugin works. It ships with the release tarball, is extracted by the control plane at install, and lands on the desktop as `~/.config/open-bot/plugin-<id>.CONFIG.md`; the agent prints it with `ob-plugin guide <id>`. Lifecycle follows the plugin: overwritten on upgrade, restored on enable and boot re-sync, removed on disable/uninstall. Because it is agent-facing instructions, the marketplace security review reads CONFIG.md on every publish as a prompt-injection surface.

## Dashboard pages

A plugin can ship a live dashboard — the **Apps** tab in the main navigation bar, where the user picks a plugin page and interacts with live data (stock lists, trackers, admin panels).

| Field | Purpose |
| --- | --- |
| `dashboard.pages.entry` | A `files[]` payload (Bun HTTP server). **Fully lazy**: the control plane starts it on the first dashboard/webhook request, restarts it on upgrade and settings saves, and stops it after a 5-minute idle window (a 30 s sweeper stops overstayers). Env: `OPEN_BOT_PAGE_PORT`, `OPEN_BOT_PAGE_TOKEN`, `OPEN_BOT_PAGE_OWNER_TOKEN`, `OPEN_BOT_PLUGIN_ID`; settings/vault arrive via `~/.config/open-bot/plugin-<id>.json`. `GET /healthz` recommended (any response counts as up; implement it so diagnostics can tell a dead app from a listening port). |
| `dashboard.pages.public` | Opt in to a public HTTP endpoint: `/hooks/<userId>/<pluginId>/<path>` (the short legacy `/hooks/<pluginId>/` form stays as an alias) behaves like a normal web server in front of the page server — any method, pages/assets/streams, WebSocket upgrades. The user-scoped URL means coexisting installs of one plugin never collide. Requests wake the desktop (25 MB cap); the response returns verbatim. Optional per-install secret makes it require authentication — send it as the `X-Open-Bot-Webhook-Secret` **header** (the `?secret=` query form is deprecated: it leaks into access logs and Referer headers). `?ob_async=1` answers 202 immediately. Manage everything on the Config page's Endpoints tab (URL, copy, test request, running state, secret); the Plugins tab → Settings dialog shows the same per-plugin. Optional `dashboard.pages.publicRoutes` narrows the endpoint to an allowlist (exact paths or trailing-`/*` prefixes, max 16): the proxy answers 404 for any other path before waking the desktop; absent the list, every route is public. Dashboard access is never narrowed, and dashboard requests additionally carry `x-open-bot-owner-token` (env `OPEN_BOT_PAGE_OWNER_TOKEN`) so owner-only routes need no second in-plugin unlock; `/hooks` never carries it and strips client copies. |
| `dashboard.tabs[].kind: "app"` | The server's UI in a sandboxed iframe, proxied under `/api/pages/<pluginId>/` (app tabs load a capability-token frame `/api/pages/_frame/<token>/…` — same mapping, prefix stripped before forwarding: the server sees the bare path). SSE and WebSockets pass through. Optional `path` (default `/`) is a plugin-server-relative route the tab opens. HTML/CSS responses get the proxy prefix injected (asset links + `<base>`); JavaScript is never rewritten, so page JS must fetch with relative paths only. |
| `dashboard.tabs[].kind: "page"` + `dataUrl` / `pollSeconds` (5-3600) | The dashboard polls `/api/pages/<pluginId><dataUrl>` — `dataUrl` is plugin-server-relative, the dashboard prepends the proxy prefix — and feeds the JSON to declarative `cards` (`$.path` bindings). No HTML needed for read-only views. |
| `dashboard.tabs[].kind: "iframe"` + `url` (https) | Embeds an external site directly; the plugin's page server is not involved. |

The proxy strips cookies/auth toward the plugin and injects `x-open-bot-page-token` (both surfaces) plus `x-open-bot-owner-token` (dashboard surfaces only); the user's dashboard session never reaches the page server. Frame tokens slide for 10 minutes per request and the dashboard remints them on a 401. Ports come from a dedicated deterministic range (4740–4759). Upgrades and settings changes restart the server so it observes new config; disable/uninstall stop it. Every lifecycle change to the page-server runtime must update this page in the same PR.

## Composer @mentions

A plugin with a page server can add dynamic entries to the chat composer's `@` menu. `dashboard.mentions[]` (max 4, requires `dashboard.pages`) declares `{section, label?, path?}` — users type `@<section>/<name>` (e.g. `@stock/Widget`). The page server answers `GET <path>` (default `/mentions`) with `{items: [...]}` (max 100; ≤ 5 aliases each). The composer lists the section when the menu opens; send-time resolution injects the same "Message references:" line as the built-in sections, and a down server degrades to a graceful "list is unavailable". Sections must not shadow the built-in ones (`personas`, `cron`, `skills`, `projects`, `reports`, `plugins`); the first enabled plugin to claim a slug wins and losers are flagged on the Plugins tab.

## Device and media access in app tabs

App-tab frames run in capability-token sandboxes (opaque origin), so a page's native `getUserMedia` never works directly. The frame shim bridges it: `getUserMedia`/`getDisplayMedia` posts a media request to the Apps tab, the user confirms in an in-dashboard consent bar, and the shell relays the live tracks over an in-page WebRTC loopback — the page gets a real `MediaStream` with no second origin. The same bridge carries geolocation, `clipboard.writeText`, and Web MIDI (consent-gated). An instance may set `OPEN_BOT_PAGES_ORIGIN` (an https host reaching the same control plane) to give frames real origins with the browser's native permission flow instead. Pages must guard `localStorage` reads, avoid `window.confirm`/`prompt`/`alert` (silently blocked), and call their API with relative paths.

## Page-server dev loop

```sh
ob-plugin page PLUGIN_ID        # {enabled, running, port, pid, desktop, note?}
ob-plugin restart PLUGIN_ID     # bounce the server (wakes a sleeping desktop)
```

The spawn writes its port to `~/.open-bot/pages/<pluginId>.port`. Click-testing goes through the managed browser on loopback (`ob-chrome navigate http://127.0.0.1:<port>/`); local installs run the checkout entry with `bun --hot`, so edits apply live. Do not pin the server to `127.0.0.1` in `Bun.serve` — the health probe runs from the control container against the desktop's container IP.

## Install surfaces

- Tools land in `/usr/local/bin/ob-plugin-<id>-*`; `apply-plugin-auth.sh` writes the vault config.
- The config guide ships to `~/.config/open-bot/plugin-<id>.CONFIG.md` when the plugin has a CONFIG.md.
- The install log on the `installed_plugins` row reverses everything on uninstall.
- Disable is deep: pauses cron, unloads OpenViking skills, drops vault config + opencode surfaces; enable restores from the stored manifest snapshot.
- Failed root setup shows **“setup failed — retry”** on the Config page's Plugins tab (`POST /api/plugins/installed/:id/setup`).

## Vault

`permissions.vaultCreate` declares key slugs the plugin owns (created empty at install); `permissions.vaultRead` consumes shared user keys. The config file's `vault` branch is generated from the key vault, so treat it as read-only — local edits are overwritten on enable/reinstall/settings changes. The durable write path is `POST /api/plugins/installed/:id/vault` (agent token, write-only — values are never returned) for slugs in that plugin's `vaultCreate`, or from the desktop: `ob-plugin vault ID SLUG=value`. The user can also fill any slug on the Config Keys page.

Plugin-declared vault keys that no shared provider owns are **merged into the Config Keys tab** — one place for every key. Deduped across plugins, each row shows its `create`/`read` access (disabled plugins get a hint chip); both surfaces write the same `user_keys` rows. From the desktop, agent sessions read them with `ob-api-key <slug>`. In [team mode](/docs/team) plugin keys stay per-user by design.

## Persistence across desktop recreates

A desktop update (or any sleep/start cycle that recreates the container) wipes the container filesystem **except** the `/home` and `/usr/local` volumes. What survives without any re-run:

- plugin tools and payload files (`/usr/local/bin/ob-plugin-<id>-*`)
- vault config (`~/.config/open-bot/plugin-<id>.json`), agentsMd files, patched `opencode.json` surfaces, and anything else under `/home/agent`

What does **not** survive: anything a setup command installed into the container layer (apt packages, `/venv`, etc.). The boot re-apply re-runs `setup.commands` right after the container starts — it is what restores them, so keep the commands idempotent and expect a freshly recreated desktop to need a few minutes before root-installed dependencies are back.

## Updates

- `installed_plugins.latest_version` refreshes from the marketplace (throttled, on `GET /api/plugins/installed`).
- `ob-plugin outdated` / `update`; dashboard **“update to v…”** button.
- `app_settings.plugin_auto_update`: `off` (default) or `stable` (auto-installs newer approved stables).
- Install policy `app_settings.plugin_install_policy`: `manual` (default, confirm dialog) or `auto` (also installs pending-review plugins).

## Local development

```sh
ob-plugin install --path <plugin-root>
```

No publish needed; Re-install re-reads the path; Remove uninstalls. Schema changes need `bun run db:generate` and an image rebuild for existing desktops.

<Callout type="warning">
`setup.commands` run as root. Install policy `auto` also installs pending-review plugins — use it only on trusted instances.
