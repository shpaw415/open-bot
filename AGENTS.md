# open-bot

Self-hosted conversational bot. The in-container agent is not a coding agent.

## Product reports

Do not list or process product reports unless the user asks. When they ask, list them:

```sh
bun scripts/reports.ts
bun scripts/reports.ts --filters status=open,kind=bug,surface=nav
```

The queue lives in the control-plane sqlite. Every desktop can file into it. Review still works.

When asked to process the queue, patch clear bugs and broken friction. Leave features and ambiguous items open until asked. Mark each shipped or rejected row:

```sh
bun scripts/reports.ts done ID --note "what changed"
bun scripts/reports.ts wontfix ID --note "why"
```

## Agent-started threads

The desktop agent starts threads with `ob-thread` (`scripts/ob-thread.sh`, seed skill `images/opencode/seed/skills/thread`). `ob-thread start [--title TEXT] [--persona NAME] [--display] [--hidden] [--dir NAME] [--message TEXT]` hits the agent route `POST /api/threads` (`apps/control/src/threads.ts`), which creates the opencode session directly (reusing cron's `createSession`) and optionally posts `--message` via `prompt_async` as the first prompt. Without `--display` the title gets the reserved `worker:` prefix, so the dashboard thread list and the media vault skip it — a hidden background-job thread. `ob-thread list` returns those hidden threads (`GET /api/threads`). `ob-thread delete ID [ID...] | --all` batch-deletes them via `DELETE /api/threads` (`{ids}`; only top-level `worker:` sessions are deletable — anything else comes back `skipped` with a reason — and each success runs the same control-plane cleanup as the dashboard's delete, `cleanupDeletedThread` in `threads.ts`). Titles cannot start with `worker:` or `cron-run:`. Visible threads appear on the next thread-list refresh (opencode's `session.created` event already triggers it). `--dir NAME` (alias `--topic`) files the new thread into a dashboard folder (`thread_dirs` + `thread_dir_assignments` tables, routes in `apps/control/src/thread-dirs.ts`, `ob-thread dirs` lists them), creating the folder when the name is new; it implies a visible thread and is refused against `--hidden`. The Threads panel renders folders as collapsible groups (unfiled threads stay in the top "Threads" group), moves threads by drag-and-drop or the thread menu, and folder mutations emit `threads.changed`. Persona delegation: `--persona NAME` resolves the persona for the agent's user via `findPersona` (`apps/control/src/personas.ts`) — exact id/name first, then typo-tolerant Damerau-Levenshtein fuzzy matching (auto-match only when one candidate is clearly closest; otherwise the 400 returns `suggestions`) — binds it in `thread_personas`, injects the persona system line into the first prompt, and returns `persona: {id, name, matched}` in the 201. Persona threads default to visible (`--hidden` forces a `worker:` background thread), so delegated teammates show on the dashboard. The seed agent has a standing team rule (seed AGENTS.md `## Team`, 2026-10-18): when a task needs skills it lacks, `ob-persona list` is the first move — delegate to a fitting teammate (respecting its skill scope) via `ob-thread start --persona`, and when nobody fits, offer the user the paths (create the persona with `ob-persona add`, install a plugin, or another way) instead of skipping. `ob-thread wait ID [--timeout MIN]` (2026-10-21) blocks until a managed thread finishes its current turn — polling `GET /api/threads/:id/status` (`threadStatus` in `threads.ts`, same manageable scope as stop/post, backed by opencode's `/session/status`) every 5 s and printing one `{id, running, state, waitedSeconds, timeout}` JSON line; `--timeout` defaults to 60 and caps at 110 minutes, and `toolLimit` in `apps/control/src/stuck.ts` gives `ob-thread wait` commands the 6× stuck budget (2 h) so a documented wait on a teammate/council member is never killed while a raw sleep loop past ~15 min still is. Existing desktops need `bun run images && bun run update` before they have the CLI and skill.

Tool contract guards (2026-10-29): desktops seed an opencode plugin (`images/opencode/seed/plugins/tool-guards.ts`; the entrypoint copies `seed/plugins/*` into `~/.config/opencode/plugins/` every boot and force-registers it in the jq merge's `.plugin` array). Its `tool.execute` hooks enforce what the built-in tools only document: `write` refuses to overwrite an existing file the session never read/wrote/edited (read-first), `write`/`edit` refuse when the file changed on disk (mtime/ctime/size stamp) since this session last read it — the parallel-teammate read-modify-write clobber becomes a re-read-and-merge error instead of silent loss — and `grep` with a file `path` is rewritten to dirname + `include=<basename>` so a file-scoped grep cannot return neighboring files' matches. Covers opencode sessions only (CLI-bridge agents keep their own tool contracts). Existing desktops need `bun run images && bun run update`.

Headless permission policy (2026-11-08): the desktop's opencode config is allow-all with a small bash denylist, and that denylist must stay anchored to real connection shapes. The seed's port denies are enumerated exactly (`*:9222*` … `*:9231*`, the managed screens' CDP ports) plus `*remote-debugging-port*` — opencode's glob matcher (`Wildcard.match`) escapes `[`/`]` literally, so a character class like `*:922[0-9]*` is a silently dead rule, and the old substring `*922*` denied evidence SHA-256 hashes and council UUIDs in command text (the agent dead-ended telling the user to "add an authorization" nothing could lift). `images/opencode/port-guard.test.ts` mirrors the upstream matcher transform exactly and pins both sides: CDP URLs and the chrome debugging flag stay denied, hashes/UUIDs/counts containing 922 pass; it fails on any bare-substring or bracket-class deny key. Because an ask can still fire on config/version drift (a renamed opencode action, a future default), the control plane now treats `permission.asked` like every other headless dead-end: `dispatchPermissionAsks` (`apps/control/src/permission-asks.ts`, wired into the EventHub observer beside the delegation wakes; `permission.asked` joined the hub's forwardable set) immediately POSTs `/permission/:id/reply {reply:"reject", message}` — the model gets corrective feedback naming the policy instead of hanging until the stuck watchdog kills the turn — and emits a `permission.notice` dashboard toast (new notice kind in `notices.ts`/`AgentNotices.tsx`, key icon in `AppHeader`). Never auto-allow: an ask is by definition outside the configured allow-all. Image + control + web changed → existing desktops need `bun run images && bun run update`.

Step caps (2026-10-24; default doubled + per-user config 2026-10-27): the seed `build` agent runs with a 512-step guard by default (`images/opencode/seed/opencode.json`, forced every boot by the entrypoint's jq merge, which also derives `agent.build-unlimited` = build minus the cap — omitting `steps` is Infinity in opencode, so the opt-out is a second agent, never `steps: 0`). The entrypoint reads the per-user override from `~/.config/open-bot/agent-cap.json` (`{stepCap}`, written by `images/opencode/apply-agent-cap.sh`; invalid/missing = 512). The user sets it in Config → Chat (« Limite d'étapes par tour », empty = default): `GET/PUT /api/agent-cap` (session auth, int 1–100000 or null) stores `desktops.agent_step_cap` (migration 0023, null = 512; `DEFAULT_AGENT_STEP_CAP`/`validAgentStepCap` in `packages/db`), `syncAgentCap` (`apps/control/src/docker.ts`) pushes the file, live-jq-merges `opencode.json`, and restarts opencode when the live value differs (busy turns drain first); the `onDesktopUp` hook re-pushes on every wake. `/api/me` carries `agentStepCap`/`agentStepCapDefault`. A turn that hits the cap is forced into a text-only reply and cannot resume, which long councils kept triggering. The caller opts out per session: `POST /api/threads` and the dashboard `POST /api/opencode/session` accept `steps: "unlimited"` (anything else 400) and map it onto the `build-unlimited` agent through `createSession` (`apps/control/src/cron.ts`); `ob-thread start --steps unlimited` (works with `--council`, so every long member is uncapped in one flag) and the blank composer's « Sans limite d'étapes » checkbox (`apps/web/src/Workspace.tsx`, rides `blankSessionBody()` into the first send) are the two surfaces. DB migration + seed/image + control + web changed → `bun run images && bun run update` for existing desktops.

Delegation wake-ups (2026-10-21): councils and persona teammates no longer strand the coordinator. `POST /api/threads` accepts `--from SESSION_ID` (the calling agent's own session id — the screen id in its system line; validated as a top-level non-`worker:`/`cron-run:` session) and, unprovided, falls back to inferring the one busy top-level chat via `/session/status`. Reading results: `ob-thread read ID [N]` (last N messages of a managed thread via the existing `/api/opencode/session/:id/message` route) and `ob-thread council status NAME` (`GET /api/councils/:name/status`, both auth paths — per-member idle/busy + last-assistant-reply tail via `lastAssistantText`). Seed skills/AGENTS.md teach the `[council:`/`[teammate]` message convention and `--from`; the per-prompt system line now calls the screen id "also your session id". Screens on agent-started threads (2026-10-21): the first prompt of every `POST /api/threads` thread (ob-thread start, council member, persona teammate) now ensures the thread screen and carries the screen id line like the dashboard/cron paths (best-effort, fallback line when still starting), and `ob-thread read` works on the agent's LLM token over the same managed scope as wait/post/stop (worker: + persona-bound). Delegated members with no explicit `--model` inherit the creator thread's stored `thread_models` pick (validated, dropped to the desktop default when it no longer validates; reported as `modelInherited`), instead of silently starting on the desktop-default provider and dying on its exhausted quota (2026-10-29). Cut-vs-done signal (2026-10-29): `lastTurnEnd` (`apps/control/src/delegations.ts`) classifies each member's newest turn from its finish reason/error (done/error/cut/empty/unknown); council status members carry `endState`/`endDetail`/`stalled` (idle + error/cut/empty), `ob-thread council status` prints a `STALLED` line, and council/teammate wakes name possibly-stalled members with verify-deliverables + `ob-thread post` relaunch instructions instead of a bare "finished their work" — deliberately no blind auto-resume. Hidden thread starts also warn (201 `warning`, `hiddenStartWarning` in `threads.ts`) naming other busy worker threads live on the shared filesystem, beyond the older same-title-only guard.

## Councils (agent teams + viewer)

The desktop agent forms an agent team with `ob-thread start --council NAME [--role TEXT]` (seed skill `images/opencode/seed/skills/council`). Council membership lives in the `councils` + `council_members` tables (migration 0014): `POST /api/threads` with `council` forces the member to a hidden `worker:` thread (refused against `--display`/`--dir`), find-or-creates the council by name (names normalize to lowercase kebab — they double as URL slugs), and binds the session with its `role`. The agent ends the reply with `![council: name](open-bot://council/name)`; `splitCouncil` in `apps/web/src/chat-view.ts` strips it and the chat bubble grows an "Open council" button that opens the viewer — a PreviewPane-style split beside the chatbox (`apps/web/src/CouncilView.tsx`, drag-resizable, fullscreen on wide screens, overlay on mobile). The pane lists members with live running/idle dots (from the shared `sessionStatus` map) and a read-only per-member transcript: `GET /api/councils/:name` (`apps/control/src/councils.ts`, cookie + LLM-token auth) merges membership with opencode session titles, and the transcript reuses `GET /api/opencode/session/:id/message` with `applyMessageDelta` + debounced refetch on member events. `ob-thread councils` lists councils, `ob-thread council close NAME` (`DELETE /api/councils/:name`) deletes every member session through the same path as `DELETE /api/threads`, runs `cleanupDeletedThread` (which now also drops `council_members` rows, so dashboard/`ob-thread delete` of a member keeps councils consistent), and keeps the council tracked when some deletes fail. Member mutations emit `councils.changed` + `threads.changed`. Task-tool subagents spawned inside a member are visible too: `councilDetail` derives a `subagents[]` list (one level deep, `{sessionId, parentId, title, createdAt}`) from the same opencode `/session` fetch it already makes — sessions whose `parentID` is a member, never stored, so they appear live (the pane refetches on `session.created`) and vanish with their session; the rail renders them under a "Subagents" group with the same dot + transcript. ## Direct browser navigation (ob-chrome)

The managed per-thread browser has a plain navigate path beside the System 1 loop: `ob-chrome` (`images/opencode/ob-chrome.sh`, `apps/control/src/nav/chrome.ts`) runs `navigate URL` (also `--url URL`, scheme optional), `url`, `back`, `forward`, `reload` against the thread's CDP port and prints one `{url, title}` JSON line. A hung or crashed renderer is a fast error, and `navigate` then recovers over plain HTTP (`PUT /json/new`, closing only the target that stopped answering) and reports `via: "new-tab"`. The browser ladder is now `ob-chrome navigate` → `ob-page` → `ob-nav` (opt-in, real multi-step page goals) → `ob-vnc` pixels; the per-prompt system line (`vncSystemLine` in `apps/control/src/screens.ts`), seed skills, and seed AGENTS.md all teach it. All CDP hops fail fast (4s `/json/list` timeout, 6s per-call, 5s ws open — `nav/cdp.ts`), and target selection prefers the first non-`about:blank` page so multi-window screens stop grabbing a blank tab. Screens self-heal: every CLI wrapper runs `screen-heal.sh` first, which re-runs `sudo screen-up.sh` (idempotent) when the thread's Xvfb or Chromium died (e.g. OOM during a cron pass); a screen whose display was taken by another session reports and stops. Screens no longer track a restore URL: url-watch and the `~/.open-bot/screens/<session>.url` state file are gone, and a relaunch always opens `about:blank` — the agent navigates back with `ob-chrome`. Screen theft hardening (2026-10-15): screen-up/screen-heal touch a `last-active` stamp that `screen-list.sh` reports and `ensureInner` merges with the DB stamp, so a CLI-active screen is never the LRU victim; `busySessions` fails closed (evicts nothing when the opencode status check fails); cron agent runs ensure the delivery-thread root's screen (one screen per cron thread, no per-fire churn); `screen-up.sh` takes a per-display flock and refuses when another live session's `run_dir/display` claims the screen and a live Xvfb still holds it (a claim whose owner has no live Xvfb is stale — a crashed owner — and is taken over; a session's own listing never blocks its own heal, so closing the last tab relaunches the browser on the next CLI call), ending the heal/ensure double-booking that let two agents drive one Chromium; and every up/down/heal/refusal appends a line to `~/.open-bot/screens.log` (asked as "who took my screen"). `ob-app launch chrome` without `--profile` now uses the default per-session profile instead of erroring `bad profile name`. DevTools data (2026-10-26): `ob-chrome console|network|metrics` read the screen's browser DevTools data — console messages, uncaught errors and failed resource loads; the request log with statuses, sizes, timings, headers and opt-in response bodies (`network N --body`); and live Performance metrics (JS heap, DOM nodes, layout counts). `ob-chrome dom` reads the live DOM (whole page HTML, `--text`, or `--selector` matches) and `ob-chrome eval "JS"` runs JavaScript in the page — the sanctioned mutate path (the agent is denied raw CDP by bash permissions); eval prints the `{url, value}` envelope like every verb, and `eval 'JS' --raw` prints the JSON value alone for polls that parse fields at the root (2026-10-29); `ob-chrome cache clear [--origin URL] [--cookies] [--reload]` busts the cache for dev (browser HTTP cache, or one origin's cache storage/service workers/localStorage/IndexedDB), and `reload --fresh` is a hard reload. A per-screen recorder (`apps/control/src/nav/devtools.ts`, started by `screen-up.sh` beside the browser and lazily respawned by the CLI) holds a CDP socket open with Runtime/Log/Network enabled and buffers events to `~/.open-bot/devtools/<session>/events.jsonl` (rotating ~2MB) — console/network events only flow while a session is attached, so the recorder is what makes them readable after the fact; response bodies evaporate once the page consumes them, so the recorder snapshots small textual bodies in memory at `loadingFinished` and serves `--body` asks through a one-shot file handshake (bodies are session-scoped for `getResponseBody`, and never touch disk). Existing desktops need `bun run images && bun run update`. Capture coordinate honesty (2026-10-29): scaled `ob-vnc capture FILE 2|3` (`images/opencode/xshot.ts`) no longer touches `Emulation.setDeviceMetricsOverride` — it shoots with a screenshot clip scale (the override set/shoot/clear churn could leave the window compositor frozen on a stale frame while the page kept rendering); only an explicit `WxH` capture still overrides, with per-call CDP timeouts and a verified, loudly-reported clear. The printed `factor` is measured from the returned PNG bytes (IHDR), the line now ends with `dpr D`, and the stored transform (`coord.ts` `toLive`: live = device-px offset + image/factor × dpr) accounts for browser zoom — as does `ob-vnc hit` (`HIT_SCRIPT` divides live device px by `devicePixelRatio` before `elementFromPoint` and reports `dpr` + the viewport point; zoomed hits used to read "outside the browser window"). ## Screen recording (ob-record)

## Managed background processes (ob-process)

The desktop agent starts long-running jobs (servers, watchers, crawls) with `ob-process` (`images/opencode/ob-process.sh`, seed skill `images/opencode/seed/skills/processes`). `ob-process start --name NAME [--session SESSION] -- CMD...` runs the command detached under `setsid`, captures output to `~/.open-bot/processes/logs/<id>.log`, and registers the job under `~/.open-bot/processes/` (`{id, name, session, pid, pgid, startTime, cmd, startedAt}`). `list [--json]` verifies liveness against `/proc` (the stored `/proc` starttime guards against pid reuse) and prunes dead rows — the log file survives so a crashed job stays diagnosable; `log ID [--tail N]` reads the captured output; `kill ID` TERMs then KILLs the whole process group. App-tab frames are capability-token sandboxes (`/api/pages/_frame/<token>/…`, no session cookie, opaque origin when `OPEN_BOT_PAGES_ORIGIN` is unset): page scripts must guard `localStorage`/`sessionStorage` reads (`SecurityError` on an opaque origin otherwise), never use `window.confirm`/`prompt`/`alert` (the sandbox silently blocks modals — they return false/null with no error; use in-page dialogs) and call their API with relative paths; the frame proxy injects a shim (`FRAME_STORAGE_SHIM` in `preview.ts`) ahead of page scripts that shadows denied storage with in-memory fallbacks and defaults fetch/XHR/EventSource to credentialed so edge SSO (Cloudflare Access) cookies ride along — the frame CORS (`pageFrameCors`) echoes the origin with `allow-credentials` instead of `*` for the same reason, on every response including 401/404. Device access: a sandboxed frame's native `getUserMedia` never works — an opaque origin is untrusted even when the parent is https (the frame inherits `isSecureContext = true` yet Chrome rejects capture with SecurityError "Invalid security origin", and `location.origin` still reports the URL origin — the opaque check must be `window.origin === "null"`). The frame shim (`FRAME_STORAGE_SHIM` in `preview.ts`) therefore bridges whenever the document origin is opaque regardless of secure-context state, and carries `data-cfasync="false"` so Cloudflare Rocket Loader never defers it past the page's own scripts. The bridge: the page's `getUserMedia({audio, video})`/`getDisplayMedia` posts `media-request` to the Apps tab, the user confirms in an in-dashboard consent bar (remembered per tab + kind), and the shell captures with its own trusted origin and relays the live tracks over an in-page WebRTC loopback (`media-offer`/`media-answer` non-trickle exchange — both sides pass `{type, sdp}` objects, never bare SDP strings, which `setRemoteDescription` rejects — `media-release` when the frame stops tracks or the PC drops) — the page gets a real `MediaStream` with no second origin, no DNS, and no external hop, working on every access path (LAN, tunnel, offline). Chrome reports `permissions.query` for microphone/camera as "denied" on an opaque origin without ever prompting, which stops pre-checking pages from calling `getUserMedia` at all — the shim answers `state: "prompt"` for the device names (microphone/camera/geolocation/display-capture/midi) and passes other names through, so the shell's consent bar stays the only real gate. The same bridge relays `geolocation` (`geo-request`/`geo-response`, consent-gated, `watchPosition`/`clearWatch` honored), `clipboard.writeText` (`clip-write`/`clip-result`, promptless — it rides the user's own click), and Web MIDI (`requestMIDIAccess` → `midi-request`/`midi-access` port snapshots, `midi-listen`/`midi-message` input relay, `midi-send`, `midi-state` on plug/unplug; consent-gated, `sysex` flagged in the bar). `enumerateDevices` returns `[]` and clipboard reads stay unavailable on same-host frames. An instance MAY still set `OPEN_BOT_PAGES_ORIGIN` (an https host reaching the same control plane; `GET /api/pages` reports `pagesOrigin`, the Endpoints tab hints when unset): frames then run as real origins (`isolated: true`, `allow-same-origin` sandbox) with the browser's native permission flow and the full delegated permission set (`appTabFrameProps` in `plugin-tabs.tsx`). When the bridge is impossible (old dashboard, no RTCPeerConnection), the shim rejects and posts `media-blocked`, which the Apps tab shows as a banner. The 12 s bridge timeouts post `media-blocked` with a reason too, and the shell preflights capture (no `navigator.mediaDevices` — e.g. the dashboard opened over plain http) answers `media-denied` with an https hint — so a stale pre-bridge dashboard shell or an insecure browsing context surfaces a precise message instead of the plugin's generic permission-denied banner. A shell-side capture failure (browser-level mic block, no device) also surfaces in the tab now: the Apps tab shows a mapped banner ("click the mic icon in the address bar", https hint, no-device) with a Retry that re-opens consent. Stale shells self-heal: every frame-path response carries `x-open-bot-build` (content hash of the web `index.html`, also `GET /api/build`), the running shell compares it on its keep-alive HEAD, and on drift shows a "Dashboard updated — reloading" overlay and reloads once (sessionStorage-guarded, deferred while a consent bar or active bridge exists). Frame tokens slide for 10 minutes per request; the Apps tab HEADs its frame every 4 minutes to keep the token alive and remints + reloads on a 401 (deploy restarts, idle expiry), skipping 502 so a cold desktop doesn't loop. The endpoint (`apps/control/src/workspace-file.ts`, route beside `/api/workspace/image` in `server.ts`) serves any allowlisted file under `/home/agent` through opencode `/file/content` re-rooted with `?directory=<dirname>` — viewable types inline (PDF, text/code as `text/plain`, audio, `.svg`), the rest as downloads, every response `nosniff` + CSP-sandboxed, 25 MB cap, protected paths (`.ssh`, `.open-bot`, `.openviking`, `.config/open-bot`, `.env`/key/auth files) refused on both sides. Bare and backticked paths in prose are linkified by `remarkAgentFiles` (`apps/web/src/file-refs.ts`, shared by chat, council transcripts, and cron results via `chatUrlTransform`), whole-line paths become embeds/links in `embedWorkspaceImages`, and a non-media file embedded with `![]()` renders as a link. In the thread workspace a click opens the split file previewer beside the chat instead of leaving it (`FilePreviewPane`/`FilePreviewOverlay` in `apps/web/src/FileView.tsx`, `?fileview=<path>` URL screen alongside `?preview=`/`?council=` — pane on wide screens, overlay on phones, drag-resizable, Back/Escape closes, in-pane file links swap the open file): markdown renders formatted through `ChatMarkdown` with relative links/images resolved against the file's folder (`basePath`), code/text as a capped `<pre>`, images/video/audio inline, PDF in a frame (the endpoint only CSP-sandboxes script-capable types so the browser PDF viewer still loads), `.glb` in the 3D viewer, everything else as a download offer; surfaces without the previewer (cron results) keep the new-tab fallback, as do modifier/middle clicks, snapshots, and media-vault links. The dashboard prompt line (`FILE_REPLY`) and seed AGENTS.md teach the `[name](/home/agent/…)` form. Seed changed → existing desktops need `bun run images && bun run update`; no DB migration.

## Split a thread at a message (branch)

Every chat bubble's meta row carries a fork action (« Nouvelle conversation jusqu’à ce message », `ForkRightIcon` beside copy/read-aloud in `MessageBubble`, `apps/web/src/Workspace.tsx`): one click creates a new thread that ends at the selected message — that message included, every older message before it, nothing after — and opens it; the source thread is untouched (no confirm, the split is non-destructive). Bubbles name their end via `VisibleMessage.lastMessageId` (`apps/web/src/chat-view.ts`, advanced on burst merges, empty on pending receipts, which show no button); the click posts it to `POST /api/opencode/session/:id/split` (cookie auth, intercepted in `apps/control/src/server.ts` before the generic opencode proxy, logic in `apps/control/src/thread-split.ts`). The copy is opencode's own fork (`POST /session/:id/fork`) — semantics probed live against 1.19.5 (2026-11-09): its `messageID` is EXCLUSIVE (the fork holds the messages strictly before it) and no boundary copies everything, so `splitForkBoundary` forks at the raw message after the selected one, or with no boundary when the selected message is the thread's last raw one. Guards: unknown message 400 `message_not_found`, subagent/hidden `worker:`/`cron-run:` threads 400, a thread with a running turn 409 `thread_busy` (the boundary could shift mid-copy; unreadable status fails closed to 502). The branch is a top-level session titled `<source> (fork #N)` by opencode and inherits the source's control-plane bindings — persona (`thread_personas`; its scope re-applies on the next dashboard prompt), model/effort pick (`thread_models`), and folder (`thread_dir_assignments`) — copied best-effort so a binding failure never strands the fork; success emits `threads.changed`. Response 201 `{id, title, sourceId, messageId, copiedMessages}`; the dashboard then opens the branch through the normal `selectThread` path. Council member transcripts (`CouncilBubble`) deliberately have no split button, like the other thread-bound bubble extras. Tests: `apps/control/src/thread-split.test.ts` (boundary + handler guards/bindings), `lastMessageId` case in `apps/web/src/chat-view.test.ts`. No DB migration, no seed/image change — control + web deploy (instance update) only.

## App-like navigation (history stack)

Every user action that opens a screen is a history entry (2026-10-30), so the system/browser Back button (Android gesture/button, iOS edge swipe, desktop Back) always dismisses the topmost thing instead of leaving the page, and Forward/reload restore the exact screen. Two mechanisms in `apps/web/src/back-nav.ts`: (1) back layers — opening a dialog, drawer, sheet, menu, lightbox or palette pushes one same-URL entry carrying `history.state.obLayers` (token stack reconciled push/back/replace, menu chains replace instead of stacking, busy/suspended layers re-arm like `suspendEscape`, Forward reopens only opt-in viewers); `useOverlayA11y` (`dialog-a11y.ts`) registers every `AccessibleDialog`, the nav/views drawers, the notifications panel and the mobile search sheet automatically, and menus, the chat lightbox, the thread-history overlay, thread batch-select mode, the home-screen folder/edit modes and the IDE quick-open/explorer call `useBackLayer` directly. (2) URL search state for content screens (param names in `routes.ts`): open chat thread (`?thread=`, localStorage demoted to bare-`/chat` restore memory, deleted threads never resurrect from stale entries), preview/council panes (`?preview=`, `?council=`, `?member=` replace), media albums/items (`?album=`, `?item=`, viewer paging replaces), project + IDE file (`?id=` push, `?file=` replace), cron editor (`?job=<id>|new` — the old clean-the-deep-link contract is reversed: Back closes through the discard confirm, a refusal re-pushes the entry, its dialog sets `disableBackClose`), admin section (`?tab=`). The shell (`App.tsx`) tags layer entries with the same `ob`/`obPos` as page pushes so `nav-guard.ts` math stays exact, pure layer pops (same full URL) skip the dirty-form prompt while search moves keep it (leaving a dirty IDE via `?id=` removal still asks), same-URL pushes are deduped (re-tapping the current nav destination is a no-op, workspace tab switches carry `?thread=`), inner `.ob-scroll` positions restore per entry (`history.scrollRestoration = "manual"`), and `data-ob-nav` gives `.ob-view-enter` a directional slide. Chat images open the lightbox on tap (touch has no hover). Deliberately not history: combobox/suggestion lists (mention, slash, model autocomplete, app launcher, desktop search), toasts/snackbars, tooltips, native fullscreen (the browser maps Back to exit), and the VNC held state. Tests: `back-nav.test.ts` (fake-history stack), `back-nav.render.test.tsx` (lightbox/dialog Back + Forward), updated cron deep-link contract. ## Per-thread model picker

The chat composer's model/effort picker is scoped to the open thread (2026-10-28): changing it writes only that thread's `thread_models` row, never the desktop default other threads read. `PUT /api/model` and `PUT /api/thinking` accept an optional `sessionId` — with it, the control plane validates and stores the pick per thread (no `desktops` write, no `opencode.json` rewrite, no opencode restart; the Config page's sessionless PUTs keep the old desktop-wide behavior and remain the only editor of the default). `GET /api/thread-model?sessionId=` returns the effective pick (explicit half wins, the other falls back to the desktop default/team overlay; a team lock overrides stored picks) plus the explicit halves. The dashboard prompt proxy stamps via `applyThreadModelChoice` (`apps/control/src/effort.ts`): the stored model fills a model-less prompt body, an explicit body model always wins, and the thread effort overrides the desktop effort only on a model that supports it. In `apps/web/src/Workspace.tsx` the picker state belongs to one named thread (`modelForRef`); a thread switch reloads its pick, a prompt sent before that lands omits the model so the server stamps the stored one, and the blank composer's pick stays local until the first send rides it on the session-create body (`model`/`thinkingEffort` in `createOpencodeSession`, dropped when team-locked or provably invalid) and re-reads the stored truth. No DB migration (`thread_models` already existed for `ob-thread` picks); control+web deploy only.

## Timeline rows, work summary, and the persisted message queue (T3-style thread UI)

The thread view renders as derived timeline rows (2026-11-02, modeled on T3 Code): `apps/web/src/timeline.ts` interleaves the transcript bubbles with one work-summary row per assistant turn — « A travaillé 2 min 14 s · 12 étapes », expandable to the step list (tool + title), live turns read « En cours » with a pulsing dot. Work aggregates from the raw messages' tool parts (burst-merged bubbles keep only their first message's parts, so bubble parts would undercount), keyed by turn = user messages seen so far; a tool-only turn with no visible bubble still gets its row. Presentation (`WorkLine`, `QueueDock`) lives in `apps/web/src/thread-timeline.tsx`. Bubbles restyled T3-like: the user pill sits on the quiet `--ob-message` surface instead of the filled primary, and each message carries a meta row underneath (time · copy · read-aloud · send mark) that surfaces on hover/focus and stays faint on touch; log, dock, and composer share the one `--ob-chat-column` width.

The waiting list is server-persisted now (it used to be dashboard state, flushed by the client): rows live in `thread_queue` (migration 0025 + `ensureThreadQueueTable`; `seq` orders, promote jumps below the min; `files` is the joined-files JSON with data: URLs). Routes (`apps/control/src/thread-queue.ts`, session auth only): `GET/POST /api/thread-queue/:sessionId`, `PATCH/DELETE /api/thread-queue/:sessionId/:itemId`, `POST .../:itemId/send-now`; cap 10, tail-dedupe on double Enter, every mutation emits `queue.changed`. The flush rides the SSE pump beside delegation wakes (`dispatchThreadQueueFlush` in `apps/control/src/index.ts`, plus a wake-time pass via `onDesktopReady` for queues left behind by a sleeping desktop): `session.idle` sends the head through `sendDashboardPrompt` (`apps/control/src/prompt-send.ts`, extracted from the dashboard prompt proxy in `server.ts` so queued sends get the identical persona/screen/reference/model stamping, model pick read at flush time as the old client flush did). The gate (`queueFlushAllowed`) fails closed on an unreadable status and holds behind an errored last turn (the old dead-turn-banner hold, via `lastTurnEnd`); send-now promotes + aborts the running turn (or force-sends when idle) and steps over the hold. The row is deleted only after opencode accepts the prompt. The idle flush is single-shot, so anything that silently drops it (a session.idle lost in an SSE reconnect gap, a transient status-fetch timeout, a failed prompt send — no turn started means no next idle) used to strand the queue until the next desktop sleep/wake; a 30 s drain (`drainThreadQueues` in `apps/control/src/thread-queue.ts`, wired in `index.ts`, backed by `db.threadQueuePairs()`) now re-runs the self-gated flush for every queued session as a backstop (diagnosed 2026-11-07 from a live stall: nine messages stuck 2h15m after a clean finish=stop turn). Queued messages render in the dashed dock at the end of the log (full text, image thumbnails, collapse past 3, « Envoyer maintenant » / in-place edit via PATCH / remove) — never as transcript bubbles, so `transcriptBubbles` lost its `queued` param and the client's `message-queue.ts` is gone. `cleanupDeletedThread`, `deleteUser`, and `resetDesktopState` clear queue rows. Accepted edges: editing is in-place in the dock (not T3's load-into-composer — the composer draft is mount-seeded from localStorage and must never be clobbered), there is no steer-into-running-turn (send-now interrupts, as force-send always did), and a process crash between prompt acceptance and row deletion can re-send once. Tests: `packages/db/src/index.test.ts` (ordering/promote), `apps/control/src/thread-queue.test.ts` (parse/gate + handler against a real Db), `apps/web/src/timeline.test.ts` + `thread-timeline.render.test.tsx`. DB migration + control + web; no seed/image change, existing desktops need only the instance update.

## Lazy thread history (paged messages)

Thread transcripts load lazily (2026-11-01): the dashboard opens a thread on its newest page and pulls older pages as the reader scrolls up, instead of downloading, holding, and rendering the whole history (thousands of raw opencode messages on long threads). The control plane pages in `apps/control/src/messages-page.ts`: `GET /api/opencode/session/:id/message?limit=N` (default 100, max 1000) returns `{messages, total, hasMore, nextBefore, startUserCount}` — the tail slice, trimmed like the full list — and `&before=<messageId>` returns the slice right before that cursor (unknown cursor is a 400 `message_cursor_unknown`, never a silent tail page). No paging params keeps the legacy plain-array response, so `ob-thread read` (same paging on the agent-token route in `apps/control/src/threads.ts`), AgentNotices, and older dashboards are untouched; the paging params are never forwarded to opencode (its API has no paging — the control→browser hop is where the bytes and tab memory are saved), and a paged ask that fails upstream answers 502 instead of falling through to the generic proxy. Client window logic lives in `apps/web/src/message-page.ts` (`parseMessagePage` — a bare array from an older control plane reads as one complete page — `mergeTailPage`, `mergeOlderPage`, `tailLimit`, `infoPredatesWindow`). In `apps/web/src/Workspace.tsx` the tick fetches `tailLimit(loaded)` = at least one page, widened to the loaded window (server cap) so edits/removals inside the window still reconcile, and merges it over the window: the older prefix survives with its cursor, no overlap resets to the fresh page. A top sentinel (`IntersectionObserver`, 400 px early, button/spinner/retry states in the row) loads older pages, walking up to 5 tool-only pages per trigger until a visible bubble lands; prepends anchor the scroll in a layout effect, and a failed older load stops auto-loading until the retry button. Send receipts keep absolute baselines: `startUserCount` (user messages before the window) feeds `transcriptBubbles`' offset and the send-time baseline, so prepends never shift a receipt onto the wrong bubble. Live `message.updated` infos predating the window are skipped instead of appended as new. The message cache (`message-cache.ts`) stores the window + its paging meta, never the full history. `CouncilView.tsx` member transcripts page identically. Accepted edges: preview/council markers older than the window surface only once their page loads (delegation watches still feed the Councils button), and a removal older than the tick's capped window reconciles on the next older-page load. Tests: `messages-page.test.ts` (control slicing/cursors), threads read route paging, `message-page.test.ts` + windowed-receipt case in `chat-view.test.ts` + cache meta in `message-cache.test.ts` (web). No DB migration, no seed/image change — control+web deploy only. Spinner trap (2026-11-02): mui-lite `CircularProgress` numeric `size` is **rem**, not MUI pixels — the sentinel's `size={14}` rendered a 224px wheel on scroll-up (same bug in `CouncilView.tsx`; `size={26}` in `Model3dView.tsx` was 416px); pixel sizes must use the string form (`size="14px"`), guarded by `apps/web/src/progress-size.test.ts`. Skeleton loading (2026-11-05): message loads show bubble-shaped skeletons, never a spinner + loading caption — `MessageSkeletons` (`apps/web/src/message-skeletons.tsx`, user/assistant shapes mirroring the timeline, loading wording kept as the `<output>` aria-label only) renders for a thread's first page (5 rows, replacing the inline copy in `Workspace.tsx`), at the top sentinel while an older page loads (3 rows, stretched to the reading column via `.ob-load-older:has(.ob-msg-skeletons)`; the load-older button and retry states stay text), and at the end of the log while a cached transcript's catch-up fetch reconciles (2 rows where newer messages land — the « Chargement des nouveaux messages… » status row above the log is gone). `CouncilView.tsx` member transcripts mirror all three (initial spinner replaced too). Tests: `message-skeletons.render.test.tsx`. Web only — no DB migration, no images/update.

## IDE type support

## Voice (browser STT + read-aloud)

Core control-plane feature (added 2026-10-09, `apps/control/src/voice-providers.ts` + routes in `server.ts`): per-user config on the `desktops` row (`stt_/tts_` provider/account/key/model, `tts_voice`, `voice_language`; migration 0002) managed via `GET/PUT/DELETE /api/voice` (keys never returned to the browser; vault fallback — Workers AI reuses the `cloudflare` slug, xAI→`xai`, OpenAI→`openai`). `POST /api/stt` takes the browser recording as multipart `audio` (25 MB cap) and returns `{text}`; `POST /api/tts` takes `{text}` (4000-char cap) and returns audio bytes (xAI `POST /v1/tts` `{text, voice_id, language}`, OpenAI `/audio/speech`, Workers AI REST `@cf/openai/whisper-large-v3-turbo` (default; the legacy `@cf/openai/whisper` literal is remapped to it, language + `vad_filter` hints attached) or `@cf/deepgram/nova-3` / `@cf/myshell-ai/melotts`). UI: hold-to-speak mic + read-aloud toggle live in `apps/web/src/Workspace.tsx` (Composer), Voice tab in Config (`VoiceProvider.tsx`); `speakableText` in `chat-view.ts` strips markdown/plugin-cards before synthesis. The desktop agent never sees audio — transcripts arrive as plain text in the prompt.

## Watchdog (model-exchange security monitor)

A security watchdog runs inside each desktop container (added 2026-10-16): `images/opencode/watchdog-daemon.ts` (spawned by the entrypoint next to the other daemons, supervisor-restarted, imports the shared `apps/control/src/watchdog-rules.ts` copied to `/opt/open-bot/watchdog-rules.ts`). It subscribes to the local opencode SSE stream (`127.0.0.1:4096/event`, Basic auth from env) and triages every exchange — user prompts, assistant responses, tool inputs, tool outputs — in **all** sessions including hidden `worker:`/`cron-run:` ones. Detection is hybrid: local rules first (injection phrasing, secret key material, piped-to-shell, docker.sock/`.ssh` writes, credential egress, watchdog tampering; snippets redacted `redactSecrets`-style before storage or reporting), and medium+ hits optionally get an LLM verdict from the user-configured provider (Workers AI / OpenAI / xAI / custom OpenAI-compatible; vault fallback for the key like Voice). Prompt-source findings are capped at medium (the human's own words never stop a turn); a benign LLM verdict downgrades to low. Findings POST to `POST /api/watchdog` (Bearer LLM token, 60/hour cap, sha256-ish fingerprint deduped 10 min), persist into `watchdog_findings` (migration 0011, pruned to 200/user), and emit `security.notice` on the hub → AgentNotices toast + native notification. Policy: **every finding alerts; high severity + `stopOnHigh` aborts the session and injects a wrap-up prompt** (same opencode calls as `stuck.ts`). The desktop also appends redacted JSONL to `~/.open-bot/watchdog.log`.

Dashboard: Config → Watchdog tab (`apps/web/src/Watchdog.tsx`) — enabled + stop-on-high toggles, verdict-provider picker (keys never returned, `keySource` like Voice), findings list with severity filters, redacted-snippet reveal, reviewed/dismiss. Seed skill `images/opencode/seed/skills/watchdog/` + a seed AGENTS.md safety bullet teach the agent to never retry or evade a stopped turn (tampering attempts are themselves high-severity findings). Config reaches the daemon as `~/.config/open-bot/watchdog.json` (`apply-watchdog.sh`, pushed on every config change, on the vault-change resync, and on every desktop start via the `onDesktopUp` hook — always the full payload so toggles survive provider removal); the daemon reloads on a 30 s mtime poll and drops its event stream when disabled. Manifest/DB changed → `bun run db:generate` done; existing desktops need `bun run images && bun run update`. Known v1 limit: image-borne (screenshot) content is not scanned.

## Persona skill scopes

A personality can carry an optional skill allowlist: threads (and cron fires) running a restricted persona see only the allowed skills in model context. Model: the `personas` row carries `skills` (base allowlist, null = all) and `skills_extra` (user extension for plugin-owned personas); `skillsEffective` is the pre-merged list every consumer reads (null = unrestricted). Enforcement rides opencode session-scoped permission rules — no opencode.json writes, no restarts: the wire shape is `{permission, pattern, action}` and the skill ruleset is one `{"skill", "*", deny}` followed by one allow per skill (find-last-match-wins makes the allows win; the seed config's `"*": "allow"` guarantees no stray ask-prompts). The array is sent once per session — in the `POST /session` body (`permission`) through cron's `createSession` (shared by `ob-thread start`, plugin cron, plugin hooks) and the dashboard new-thread route — and re-applied fire-and-forget via `PATCH /session/{id}` on every dashboard prompt of a persona-bound thread (covers persona edits, opencode restarts, and binding moves). Rules persist in opencode.db, so they survive `restartOpencode`. `applyPersonaScope` (`apps/control/src/personas.ts`) is the shared helper; failure degrades to unrestricted, never blocks.

**MCP scopes work the same way** (migration 0016 added `personas.mcp`/`mcp_extra`): a persona with an `mcp` allowlist sees only the listed servers' tools, and MCP is three-state — null = all servers (the default), a name list = allowlist, **an explicitly empty list = every server blocked** (`mcpEffective` keeps `[]`; extras cannot resurrect a block-all base). The shape differs from skills because the tool-map filter disables a tool only when the last rule matching its id is a pattern-`"*"` deny — so denies are enumerated per unlisted configured server as `{permission: "<server>_*", pattern: "*", action: "deny"}` (a `"*"` permission would strip the builtin tools too; verified in opencode 1.19.3: MCP tools execute under `permission: <toolid>`, and a server whose tools are all disabled also loses its `<mcp_instructions>` block). The configured-server list comes from `readMcpConfig` at scope-apply time — only for MCP-restricted personas, degrading to skills-only rules when the desktop cannot answer. Server-name validation uses the `mcp` NAME pattern (letters/digits/dots/hyphens/underscores, glob-free), max 16.

**Block-all (disable everything)** (migration 0021 added `skills_none`/`mcp_none` on `personas` and `builtin_persona_scopes`): an explicit flag that blocks every skill or MCP server on **any** persona kind — the only way to do that on a locked base (plugin/built-in), where emptying the base list is impossible. `skillsEffective`/`mcpEffective` return `[]` when the flag is set; the skill ruleset for `[]` is a lone `{"skill","*","deny"}` (the whole skill tool disappears from the tool map — that is the point), and the MCP half denies every configured server. The flags win over lists; a `PUT` carrying a non-empty `skills`/`mcp` list clears the flag (they contradict). `PUT /api/personas/:id` accepts `skillsNone`/`mcpNone` booleans on custom, plugin-owned, and built-in personas; `ob-persona --skills none` / `--mcp none` set them (and a list or `--skills-clear`/`--mcp-clear` lifts the block); the dialog pickers carry a "Block all skills / servers" chip on every persona kind, and a built-in's flag short-circuits the seed/MCP probes so blocking works even when the desktop cannot answer. `personaSystem` says "No skills load in this thread" / "No MCP server loads in this thread" for blocked personas.

User extension: `PUT /api/personas/:id` is present-set/omitted-keep — `skills`/`mcp` replace the base lists of a user persona; on a plugin-owned persona they 409 (`managed by <plugin> — extend with skillsExtra/mcpExtra instead`) and `skillsExtra`/`mcpExtra` replace the extras. Validation is reject-never-sanitize: slug-pattern skill names and the MCP server-name pattern only (glob characters `* ? [ ]` are refused — a stray `*` would re-open everything under opencode's minimatch), max 64 skills / 16 servers, trimmed, deduped; empty list = all. `GET /api/personas/skill-catalog` (registered before the id regex) merges desktop seed skills (`~/.config/opencode/skills/*/SKILL.md` frontmatter) with OpenViking skills plus the configured MCP servers (with plugin owner names), deduped; a sleeping desktop answers empty lists with `live: false` (MCP-tab down-pattern). `ob-persona` gains `--skills "a,b,c"` / `--mcp "a,b"` (replace the editable lists; `--mcp none` blocks every server), `--skills-append NAME`/`--skill` and `--mcp-append NAME` (repeatable, comma lists), `--skills-remove NAME`/`--skill-remove` and `--mcp-remove NAME` (drop names from the editable list — the extras on plugin/built-in personas, the base on user personas; a locked-base name is refused as always-allowed, an unrestricted user persona is refused with a set-a-list-first hint, and emptying a user persona's skill list is refused in favor of `--skills none`/`--skills-clear`), `--skills-clear`/`--mcp-clear`; on plugin personas the replace flags target the extras and refuse base names. `list_to_json` in `ob-persona.sh` slurps with `jq -Rs` and splits on comma/whitespace runs — the repeatable flags accumulate names with embedded newlines, and a per-line `-R` emitted one array per line, which made every single-name `--skills-append`/`--mcp-append` call die on the length guard ("Illegal number") before this fix. The dashboard Personalities dialog has two filterable chip pickers (plugin bases locked under "From <plugin>", extras under "Added by you"; catalog failure falls back to free-text entry), and persona cards show "N skills only" / "N servers only" chips.

Plugins declare per-persona scopes in the manifest (`personas[].skills` and `personas[].mcp`, mirrored in the JSON schema; `pluginPermissionSummary` adds `Limits persona "X" to skills/mcp servers: …` to the consent dialog). Apply writes both lists on create and refreshes them only when this install created the row (name-match can adopt a foreign persona — never touched); the extras are left alone in both paths. Names that resolve nowhere (desktop seed dir, OpenViking, plugin-installed skills, configured MCP servers) land in `applied.warnings` on the install log. Marketplace listing shows the lists and the security review prompt covers capability-scoping concerns for both. `GET /api/opencode/session` `startThread` responses report `persona.skills: {allowed: N}` and `persona.mcp: {allowed: N}` for restricted personas (built-ins report `{seedDefault: true, extra: N}`). Subagent asymmetry: task-tool subagents inherit only the deny rules from the parent session, so allowed skills are denied inside subagents of a scoped thread — fail-closed, documented, not fixed. Scopes curate what the agent is shown; they are **not** a security boundary (the static AGENTS.md skills index still lists every seed name, and the agent can read any skill file or talk to a denied MCP server through plain `curl`). Manifest/schema changed → `bun run db:generate` done (0015 skills, 0016 mcp); existing desktops need `bun run images && bun run update`.

**Built-in personas are seed-scoped by default** (migration 0020 added `builtin_persona_scopes`): all four code-built personalities (Assistant, Designer, Political expert, Software designer) carry a locked base — the desktop's seed skills (`~/.config/opencode/skills`, the catalog's `seed: true` set) plus every configured MCP server **no plugin owns** — instead of unrestricted access, so plugin-installed skills/servers stop flooding every persona thread. The base is computed live in `personaScope` at apply time (seed disk probe + `readMcpConfig` filtered through `pluginMcpOwners`); the user extends it with `skillsExtra`/`mcpExtra` stored in `builtin_persona_scopes` (per user+persona, wiped by `deleteUser`). `PUT /api/personas/:id` accepts only `skillsExtra`/`mcpExtra` on a built-in (name/instruction 400, `skills`/`mcp` 409 — no allow-all opt-out; custom personas keep null = all). The Assistant is now a real scoped persona: it binds in `thread_personas`, rides the session-create ruleset and the per-prompt re-apply (an **unbound** thread — no persona row — stays unrestricted), and its `personaSystem` line is the scope clauses alone. `personaSystem` for built-ins names the seed default plus the added entries instead of enumerating (the base is not synchronously enumerable), and the view's `skillsEffective`/`mcpEffective` stay null for built-ins (locked base; the UI reads the catalog). ## Application modes

The host runs in one of two application modes — a whole-host toggle the admin owns on the Admin page (`apps/control/src/team.ts`, config stored in `app_settings.team_config`; migration 0013 added `team_keys` + `user_quotas`). The old Host tab is gone (2026-10-21): the Team tab now carries everything — mode, shared keys + overlay, per-user limits, the host-wide media caps (chat media snapshots + media vault, `GET/PUT /api/admin/settings`), the host-wide "Desktop disk max", and the factory-reset danger zone. The toggle works as follows: `personal` (default, unchanged per-user keys) and `team`, where the admin sets one shared keyset (`team_keys`) plus a provider overlay (`providers.chat/image/video/model3d/system1/voice/watchdog` in the team config) that overlays every desktop's own provider rows — overlay fields win when non-null, personal keys are ignored (not deleted), and there are no personal overrides for the shared surfaces; `effectiveUserKey` (`team.ts`) is the single read path (team mode reads `team_keys` only, no personal fallback) and every resolver — image/video/model3d/system1/chat keys in `key-vault.ts`, `resolveVoiceConfig`, `resolveWatchdogConfig` — flows through it, so desktop boot, fan-out, and `resolveDesktopProviders` all inherit team keys with no other changes. Per-user even in team mode: `ttsVoice`/`voiceLanguage`, watchdog `enabled`/`stopOnHigh` (unless `lockWatchdog`), and plugin-declared vault slugs (the plugin key catalog stays per-user by design; in team mode `PUT/DELETE /api/keys` answer `403 {error:"team_locked"}` only for shared provider slugs — admins manage those via the admin routes, `keysTeamLocked` in `apps/control/src/api-keys.ts` is the predicate — while plugin-declared slugs stay writable by their owner on the Keys tab, whose provider section is read-only in team mode and whose `GET /api/keys` reports built-in slugs from `team_keys` plus `team: {mode, lockModelPicker, lockWatchdog}`). The OpenCode provider auth is shared too in team mode: a snapshot of the admin desktop's `auth.json` (api + oauth entries) lives in `app_settings.team_opencode_auth` and is merged into every desktop by `apply-opencode-auth.sh` on start/wake and team fan-outs — shared entries overwrite same-provider ids, other providers survive. Capture is automatic after every successful admin provider login/logout (`finishLogin`/`/api/providers/logout`) plus the Synchronize button on the Admin Team tab (`POST /api/admin/team/opencode-auth/sync`); non-admins get `403 team_locked` on the Providers login/logout flows and a read-only page. `lockModelPicker` makes the team chat `{provider, model}` the forced selection for non-admins (`PUT /api/model` → `403 {error:"team_locked"}`; `/api/me` + `/api/providers` report the effective selection); unlocked, a personal selection wins once set and the team value is only the default. Quotas apply in both modes (admin-role users exempt): `weeklyTokens` per user or `quotaDefaultTokens` host default, windows are UTC Monday 00:00, `0` = unlimited, and `handleLlm` returns `429 {error:"weekly quota reached", quota}` in `block` mode or adds `x-open-bot-quota: warn` (streaming + JSON) in `warn` mode. The same Admin page table ("Per-user limits" in the Team tab, 2026-10-21) sets per-user desktop resources: `desktops.memory_mb` (real cgroup cap on the opencode container, 512 MB–64 GB, NULL = the 4g default; `startDesktop` passes `--memory` at creation and `applyDesktopMemoryLimit` in `docker.ts` retunes a running container live via `docker update --memory/--memory-swap`; lowering below current usage can OOM-kill the desktop, which the crash-restart sweep recovers), `desktops.cpu_cores` (same shape for the opencode CPU allotment, 0.5–host core count — `hostCpuCores()` in `docker.ts` reads `docker info` NCPU and the quota PUT rejects caps above it; NULL = the 2-core default, setting it to the host core count takes every core the host has; `applyDesktopCpuLimit` retunes a running container live via `docker update --cpus`) and `desktops.disk_gb` (display-only Hardware-view disk cap for that user, overriding the host-wide `desktop_disk_max_gb`; `effectiveDiskMaxGb` in `stats.ts`). The quota routes carry them: `GET /api/admin/team/quotas` rows gain `memoryMb`/`diskGb`/`cpuCores` (plus `hostCores` at the top level), and `PUT /api/admin/team/quota` accepts optional `memoryMb`/`diskGb`/`cpuCores` (validated by `validMemoryMb`/`validDiskGb`/`validCpuCores` in `@open-bot/db`; present-set/omitted-keep, null clears) and answers `{ok, weeklyTokens, memoryMb, diskGb, cpuCores, memoryApplied, cpuApplied}` — `memoryApplied: false` means the desktop wasn't running, so the cap applies on its next start. Sidecar containers (viking, computer) keep fixed limits. Overlay secrets never leave the server: `redactTeamConfig` (`team.ts`) nulls `apiKey`/`gatewayToken`/`sttApiKey`/`ttsApiKey` in every response and adds a per-section `secrets` map (`{hasKey, hasGatewayToken?}`). Overlay saves merge per field (`saveTeamConfig`): a present field sets it (`""`/`null` clears), an omitted field keeps the stored value — so the admin UI's blank secret inputs never wipe a saved key. Team-mode writes are gated for non-admins: image/video/model3d `PUT`/`DELETE` and watchdog-config `DELETE` are shared surfaces and answer `403 {error:"team_locked"}` outright; voice and watchdog-config `PUT` accept partial bodies with only the per-user fields (`{tts:{voice}, language}` / `{enabled, stopOnHigh}` — absent fields keep the stored config via `applyVoicePatch`/`applyWatchdogPatch`) and reject any body that also carries shared fields with the same `403`; admins always write. Admin routes (admin-session auth, `handleAdmin` in `apps/control/src/admin.ts`, fan-out via `applyTeamChange` in `apps/control/src/team-apply.ts` which re-syncs image/video/model3d/system1/watchdog/chat auth per desktop, never aborting on a down desktop — misses re-sync at boot): `GET /api/admin/team` → `{config, secrets, catalog, keys}` (redacted), `PUT /api/admin/team` (Partial<TeamConfig>; `providers` merges per field) → `{config, secrets}` (redacted), `PUT /api/admin/team/keys` (`{slug, ...fields}`; blank fields keep the stored value — shared keys are replaced, not cleared) → `{keys}`, `POST /api/admin/team/import` (copies the admin's user_keys + provider rows into the shared config and flips mode to `team`) → `{config, secrets, keys}`, `GET /api/admin/team/quotas` → `{default, behavior, hostCores, users}`, `PUT /api/admin/team/quota` (`{userId, weeklyTokens}` plus optional `memoryMb`/`diskGb`/`cpuCores`) → `{ok, weeklyTokens, memoryMb, diskGb, cpuCores, memoryApplied, cpuApplied}`. Migrations 0013 + 0019 + control/web changed → existing desktops need `bun run images && bun run update`; deploy is control+web only (no image content change).

## Cron result thread access

Cron results are published into the job's delivery thread (`cron_jobs.session_id`, shared by all plugin guard jobs), but the Automations view only ever showed the clipped notice summary in a dialog — there was no way to reach that thread from a job or its result. `CronView` now takes `onOpenThread` (wired per pane in `App.tsx` like Dashboard/AppHeader) and shows « Ouvrir le fil » on the job card (when `sessionId` is set) and in the result dialog (resolved from the notice's job), so the full result, its files/screen, and follow-up prompts are reachable in the thread the cron job created. Web only — no DB migration, no images/update.

## Plugin guard jobs grouped (Automations)

The plugin publish guards no longer mix into the Automations list one card per published plugin (2026-11-05): `partitionGuardJobs`/`isGuardJob` in `apps/web/src/CronView.tsx` split the shown jobs on the `plugin:<id>:guard` name (the same contract as `GUARD_JOB_RE` in `apps/control/src/cron.ts`) and every guard renders under one « Garde des plugins » collapsible after the user's own automations (the shared guard thread's title; the job card itself is shared via `renderJobCard`). The section is collapsed by default with the choice persisted (`ob-cron-guards-open`), its header carries the guard count plus the « nouveau résultat »/« échec » signals so a collapsed guard that produced something or failed is never invisible, and inside it a guard card is titled by its plugin instead of the identical stripped "guard". Search/filter runs before the partition, so the header count shows matches and an all-guard result keeps an explicit list.
