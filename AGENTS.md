# open-bot

Self-hosted conversational bot. The in-container agent is not a coding agent.

## Product reports

Do not list or process product reports unless the user asks. When they ask, list them:

```sh
bun scripts/reports.ts
bun scripts/reports.ts --filters status=open,kind=bug,surface=nav
```

The queue lives in the control-plane sqlite. Desktops file into it only after `bun run update -- --dev`. A later update without `--dev` stops filing. Review still works.

When asked to process the queue, patch clear bugs and broken friction. Leave features and ambiguous items open until asked. Mark each shipped or rejected row:

```sh
bun scripts/reports.ts done ID --note "what changed"
bun scripts/reports.ts wontfix ID --note "why"
```

## Projects list

The desktop agent registers an existing folder with `ob-project add --path ~/project/user-project` (`scripts/ob-project.sh`, seed skill `images/opencode/seed/skills/project`). The path must already exist under `/home/agent`. `list` and `remove` use the desktop LLM token on `GET/POST /api/projects` and `DELETE /api/projects/:id` only; file, search, and terminal routes stay session-only. Remove unlinks the row and keeps the files. Create and delete emit `projects.changed` so the Projects tab and `@projects` mentions refresh. Existing desktops need `bun run images && bun run update` before they have the CLI.

## Agent-started threads

The desktop agent starts threads with `ob-thread` (`scripts/ob-thread.sh`, seed skill `images/opencode/seed/skills/thread`). `ob-thread start [--title TEXT] [--persona NAME] [--display] [--hidden] [--message TEXT]` hits the agent route `POST /api/threads` (`apps/control/src/threads.ts`), which creates the opencode session directly (reusing cron's `createSession`) and optionally posts `--message` via `prompt_async` as the first prompt. Without `--display` the title gets the reserved `worker:` prefix, so the dashboard thread list and the media vault skip it — a hidden background-job thread. `ob-thread list` returns those hidden threads (`GET /api/threads`). Titles cannot start with `worker:` or `cron-run:`. Visible threads appear on the next thread-list refresh (opencode's `session.created` event already triggers it). Persona delegation: `--persona NAME` resolves the persona for the agent's user via `findPersona` (`apps/control/src/personas.ts`) — exact id/name first, then typo-tolerant Damerau-Levenshtein fuzzy matching (auto-match only when one candidate is clearly closest; otherwise the 400 returns `suggestions`) — binds it in `thread_personas`, injects the persona system line into the first prompt, and returns `persona: {id, name, matched}` in the 201. Persona threads default to visible (`--hidden` forces a `worker:` background thread), so delegated teammates show on the dashboard. Existing desktops need `bun run images && bun run update -- --dev` before they have the CLI and skill.

## Native apps on the thread screen

Each thread screen (Xvfb + openbox in the opencode container) can run native apps: the agent installs them with `sudo apt-get install` (persisted across updates by `record-apt.sh`/`restore-apt.sh`) and launches them with `ob-app` (`images/opencode/ob-app.sh`, seed skill `images/opencode/seed/skills/apps`). `ob-app --session SESSION launch APP` starts the app maximized on that thread's display and tracks its pid under `~/.open-bot/apps/<session>/`; `list`/`focus`/`close` manage it (wmctrl/xdotool); `screen-down.sh` sweeps leftover pids. `ob-app launch chrome [URL] [--profile NAME]` opens a standalone Chrome with its own profile under `~/.config/apps/chrome/` — the managed per-thread browser (ob-nav/ob-page/CDP) is untouched, and `chromium`/`google-chrome` stay denied in bash permissions. `ob-app catalog` lists installed apps from `.desktop` files; the dashboard Desktop tab has an autocomplete launcher (`GET /api/desktop/apps`, `POST /api/desktop/apps/launch`, `apps/control/src/apps.ts`) that starts any catalog app on the current thread's screen. The screen has no audio stack — apps render but are silent. Existing desktops need `bun run images && bun run update -- --dev` before they have the CLI and skill.

## Plugin reports (ob-report)

While the desktop agent builds, stress-tests, or exercises a plugin from a local checkout, it files bug/friction/feature findings with `ob-report` (`scripts/ob-report.sh`, seed skill `images/opencode/seed/skills/report`). Reports are plain JSON files under `~/.open-bot/reports/` on the desktop — no control-plane token, shared by every session thread there. Dedupe by kind+plugin+title bumps hits; 8 new reports/hour; `done` reports re-open as new rows when the defect reappears. The control plane reads them by exec (`apps/control/src/reports.ts`): `GET /api/reports?status=&plugin=` and `PATCH /api/reports/:id` (emit `reports.changed`). Dashboard: Reports entry in the Views drawer (read, filter, done/wontfix/reopen, copy `@reports/<slug>`), and `@reports/<plugin>` mentions resolve per plugin in the composer and prompt references like `@projects`. Core on all desktops (not dev-gated); existing desktops need `bun run images && bun run update`.

## Plugin dashboard pages

A plugin can ship a live dashboard: `dashboard.pages: {entry}` names a `files[]` payload (Bun HTTP server) that the control plane starts on the desktop (`apps/control/src/plugin-pages.ts`; env `OPEN_BOT_PAGE_PORT`/`OPEN_BOT_PAGE_TOKEN`/`OPEN_BOT_PLUGIN_ID`, config via the shared `~/.config/open-bot/plugin-<id>.json`, `GET /healthz` recommended) and proxies same-origin at `/api/pages/<pluginId>/*` with cookies stripped, streaming/SSE pass-through, and WebSocket upgrades. `dashboard.tabs[]` gains `kind: "app"` (the plugin's full UI in the Dashboards view; optional `path`) and `kind: "page"` + `dataUrl`/`pollSeconds` (dashboard polls JSON into the declarative cards). Tabs left the top AppBar — the workspace Views drawer has one Dashboards entry listing every enabled plugin's tabs (`plugin-tabs.tsx`). Supervisor lifecycle: started at install/enable/boot re-sync, restarted on upgrade and settings changes, stopped on disable/uninstall; lazily restarted by the proxy on first request when down (ports 4740-4759 deterministic per plugin). Reference plugin: `examples/stock-dashboard` (validate with plugin-kit, install with `ob-plugin install --path`). Manifest/schema changed → existing desktops need `bun run images && bun run update`.

## Media vault

The Media tab in the workspace Views drawer lists albums of immutable copies (`DATA_DIR/media-vault`). Chat images, video, and `.glb` are filed into a per-thread album on `session.idle` (hidden `worker:` and `cron-run:` sessions are skipped). The agent files other allowlisted files, or a named album, with `ob-media` (`scripts/ob-media.sh`, seed skill `images/opencode/seed/skills/media`). Cookie and LLM-token routes live under `/api/media/*` and emit `media.changed`. Deleting a thread does not delete the album. Cap is `app_settings.media_vault_cap_mb` (default 3 GB, 0 clears). Existing desktops need `bun run images && bun run update -- --dev` before they have the CLI.

## Thread preview

The desktop agent can serve a Bun dev server and embed it in the thread (`images/opencode/seed/skills/preview`, `ob-preview`). The reply marker is `![title](open-bot://preview)`. The control plane proxies an allowlisted port (`4700–4719`) through a capability-token frame URL. On a wide screen, Open lifts that iframe into a resizable pane beside the thread; on a narrow screen it covers the viewport. Existing desktops need `bun run images && bun run update -- --dev` before they see the skill and CLI.

## Voice (browser STT + read-aloud)

Core control-plane feature (added 2026-10-09, `apps/control/src/voice-providers.ts` + routes in `server.ts`): per-user config on the `desktops` row (`stt_/tts_` provider/account/key/model, `tts_voice`, `voice_language`; migration 0002) managed via `GET/PUT/DELETE /api/voice` (keys never returned to the browser; vault fallback — Workers AI reuses the `cloudflare` slug, xAI→`xai`, OpenAI→`openai`). `POST /api/stt` takes the browser recording as multipart `audio` (25 MB cap) and returns `{text}`; `POST /api/tts` takes `{text}` (4000-char cap) and returns audio bytes (xAI `POST /v1/tts` `{text, voice_id, language}`, OpenAI `/audio/speech`, Workers AI REST `@cf/openai/whisper` / `@cf/myshell-ai/melotts`). UI: hold-to-speak mic + read-aloud toggle live in `apps/web/src/Workspace.tsx` (Composer), Voice tab in Config (`VoiceProvider.tsx`); `speakableText` in `chat-view.ts` strips markdown/plugin-cards before synthesis. The desktop agent never sees audio — transcripts arrive as plain text in the prompt.

## Hardware view

The Workspace Views drawer has a Hardware tab (`apps/web/src/Hardware.tsx`) showing the desktop container's disk, RAM, and CPU usage against max (`GET /api/hardware`, `apps/control/src/stats.ts`). RAM/CPU max come from the container limits (`--memory 4g --cpus 2` via docker inspect); usage comes from `docker stats --no-stream`, and disk is the desktop's own footprint — `docker ps -as` writable layer plus `du -sb` of the /home/agent and /usr/local volumes, not the host drive (`df -PB1 /` only supplies the fallback max when no cap is set) — and CPU renders as cores of the allotment. A sampler in `apps/control/src/stats.ts` (started from `index.ts`) records a sample every 30 s into an in-memory ring buffer (60 samples ≈ 30 min, lost on control restart; it never wakes a sleeping desktop, but opening the view does, like Reports/Media). Meters turn warning at 80% and error at 90%. Disk max defaults to the size `df` reports; `app_settings.desktop_disk_max_gb` (Admin page, "Desktop disk max") overrides it, 0 = full disk — display-only, nothing is pruned.

## System 1 CLI (ob-system1)

General-purpose access to the System 1 decision model behind `ob-nav` (Laya, Clef, or Jev — whichever the Config page configures). `apps/control/src/nav/ob-system1.ts` (copied into the image with the rest of `nav/`) plus shim `images/opencode/ob-system1.sh` at `/usr/local/bin/ob-system1`. It reuses `~/.config/open-bot/system1.json` + `system1-auth.json` — no new config. `ob-system1 --state TEXT --choice "Q?" a b [--score "Q?" [LEVEL...]] [--noul Q] [--image FILE|-]... [--image-base64 B64|-]... [--model X] [--timeout MS]` builds `q1..qn` questions from the flags (choice needs ≥2 options; score takes optional 2–10 level labels, default 5-point Likert, sends them as the criteria array and translates the returned level index into a `level` label), POSTs one `/v1/systemone` decision, and prints one JSON line `{"ok":true,"provider","model","answers":{...},"ms"}` (`valid:false` marks an out-of-list pick). Piped stdin becomes the state when `--state` is missing. Images (jpeg/png/webp, max 4, magic-byte sniffed) are provider-shaped by `decisionBody` (Workers AI objects vs llama.cpp data URLs) and hard-error on non-vision providers (Jev/Laya). `--state` twice is a usage error; `--help` prints plain text and exits 0. One retry after 1 s on 429/5xx/network only (other 4xx fail fast with the server body redacted into `detail`, 240-char cap); timeout 8 s text / 20 s vision. Exit 0 ok (incl. `--help`) / 1 error / 2 usage / 3 unconfigured. Logs `{cli:true}` rows with per-attempt ms to `~/.open-bot/system1.log` (never image bytes; the `.open-bot` dir is created if missing). Stress-tested via desktop-agent threads 2026-10-11: 7 ob-report findings (help exit code, duplicate `--state`, opaque HTTP errors, missing log dir, score criteria array, cumulative retry ms, clef-server auth) — six fixed, one wontfix (clef deployment concern). Seed skill `images/opencode/seed/skills/system1` (entrypoint copies it like the other seeds). Existing desktops need `bun run images && bun run update` before the shim and skill appear.

## Plugin system + marketplace

Plugins extend the desktop agent (skills, personas, cron, desktop tools, vault keys, dashboard tabs, chat composer features, OpenCode plugins/MCP). One manifest (`open-bot.plugin.json`; JSON schema `packages/plugin-kit/schema/open-bot.plugin.schema.json`, seeded into desktops at `~/.config/opencode/skills/plugin/` and referenced by `ob-plugin new` scaffolds — keep it in sync with the `validatePluginManifest` constants, enforced by `schema.test.ts`) describes everything; GitHub repos hold the code and releases, `apps/marketplace` (frame-master cloudflare-nextjs on Cloudflare Pages + D1) is the searchable index, review queue, and agent discussion board.

- Control plane: `apps/control/src/plugins.ts` (routes under `/api/plugins/*`, agent auth via llm token like cron/personas), `apps/control/src/plugins-apply.ts` (apply/uninstall engine; install log on the `installed_plugins` row reverses everything).
- Desktop: `scripts/ob-plugin.sh` (`new/validate/publish/search/install/...`), seed skill `images/opencode/seed/skills/plugin`, `apply-plugin-auth.sh` writes `~/.config/open-bot/plugin-<id>.json`, plugin tools land in `/usr/local/bin/ob-plugin-<id>-*`.
- Payload files: manifest `files[]` (`{name, source, exec}`) are fetched from the reviewed release tarball at install (`GET /api/plugins/<id>/artifact` streams the R2 object; control verifies sha256, extracts, installs next to tools; boot re-syncs them). Text files only; for payloads too big to inline as `tools[]`.
- Agent surfaces: `opencode.agents` registers new agent workers (deep-merged into `opencode.json`, reserved names rejected); `opencode.agentTools` patches tool globs on existing agents (e.g. `{"build": {"blender_*": false}}`); `opencode.agentsMd` injects standing instructions next to AGENTS.md (file under `~/.config/open-bot/agents-md/`, entry in the `instructions` array); plugin disable/enable and uninstall reverse them. Helper sessions a plugin spawns must be titled with the `worker:` prefix so the dashboard thread list hides them (like `cron-run:`).
- Setup commands: manifest `setup.commands` run as root in the desktop at install and re-run after every desktop recreate (`onDesktopReady` hook → `reapplyPluginSetup`; the update recycle waits for that re-run before exiting, so it must be idempotent), `setup.uninstall` runs best-effort at uninstall. Commands appear in the consent dialog and are security-reviewed; output logs to `~/.open-bot/plugin-init/<id>.log`.
- Publishing auto-creates a daily guard cron `plugin:<id>:guard` — the creator agent keeps the GitHub repo and marketplace discussion healthy. `ob-plugin guard off <id>` deletes it when maintenance stops; `ob-plugin doctor <dir>` pre-checks manifest + repo + tag before a first publish.
- Dev tags for staging: `version` accepts semver (`X.Y.Z`, optional `-prerelease`) or a dev tag (`beta-1`; `DEV_VERSION_PATTERN`/`isDevVersion` in plugin-kit). Dev publishes get the same security review but never move `plugins.latest_version` (hidden from marketplace search); install with `ob-plugin install <id> --version beta-1`, overwrite by republishing the same tag (upsert re-reviews + re-stores the R2 tarball, force-move the git tag) and reinstalling; dev artifacts bypass the control artifact cache (`plugin-artifact.ts`), so reinstalls and boot re-syncs pick up republished builds; the dashboard Plugins tab has a version picker (dev badges), a Re-install action, and uninstall. `ob-plugin publish <dir> --dev` automates the whole loop (commit → push → force-move tag → clobber release → publish → review wait → pinned reinstall).
- Updates: `installed_plugins.latest_version` is refreshed from the marketplace (throttled, fire-and-forget on `GET /api/plugins/installed`); `ob-plugin outdated`/`update`, dashboard "update to v" button, optional `app_settings.plugin_auto_update` = `off` (default) | `stable` (auto-installs newer approved stables) toggled from the Plugins page policy row.
- Lifecycle: disable is deep — pauses the plugin's cron jobs, unloads its skills from OpenViking, drops `~/.config/open-bot/plugin-<id>.json` (vault secrets) plus the opencode surfaces; enable restores everything from the stored manifest snapshot. Failed root setup shows "setup failed — retry" (dashboard) / `POST /api/plugins/installed/:id/setup`.
- Typed configs: `configs[]` entries take `type` (`string` default, `bool`, `number`, `enum` + `options[]`, `secret`; legacy `secret: true` still works); settings PUT validates/coerces via `validateConfigValue` (unknown keys rejected), upgrades prune keys the new manifest drops, and the Plugins page renders switch/number/select/password inputs (saved values now load instead of defaults).
- Event hooks: manifest `hooks[]` (max 8; `{event: "session.idle"|"thread.created", message}`) run the message as a prompt in hidden `worker: plugin-<id> <event>` sessions via the EventHub observer (`plugin-hooks.ts`); loop-guarded (worker/cron sessions never re-trigger, 20 runs/day per plugin, 2 concurrent per event).
- Plugin notifications: `permissions.notifications: true` + `ob-plugin notify <id> "title" [body]` → `POST /api/plugins/notice` (403 without the permission, 409 disabled, 30/hour per plugin) → `plugin.notice` hub event → dashboard toast + native notification in AgentNotices.
- Local development: `ob-plugin install --path <plugin-root>` installs a desktop directory into the installed list without a marketplace publish. The Plugins page shows `(local)` beside the name; Re-install re-reads that path and Remove uninstalls it. `source` and `local_path` live on `installed_plugins`.
- Install policy (`app_settings.plugin_install_policy`): `manual` (default, confirm dialog) or `auto` (no restriction, also installs pending-review plugins). Toggle on the Plugins page (admin).
- Marketplace config for the control container (deploy/.env): `OPEN_BOT_MARKETPLACE_URL`, `OPEN_BOT_MARKETPLACE_TOKEN`, `OPEN_BOT_GITHUB_TOKEN` (agent identity, injected into desktops for gh/git).
- Marketplace secrets: `MARKETPLACE_TOKEN` (instance writes), `ADMIN_TOKEN` (review queue), optional `GITHUB_TOKEN` (README fetch + security-issue filing). D1 migrations: `apps/marketplace/migrations`; deploy `bun run --cwd apps/marketplace deploy`.
- Auto security review (marketplace, on publish): `POST /api/publish` enqueues `{pluginId, version, enqueuedAt}` on Cloudflare Queue `open-bot-marketplace-security` (Pages producer binding `SECURITY_REVIEW`) and returns immediately. Poll `GET /api/plugins/:id/review?version=` (same auth) for `queued | running | pass | concern | error`. The consumer is a separate Worker (`apps/workers/review-worker`, name `open-bot-marketplace-review`) because Pages cannot consume queues. Push to `main` deploys it through Cloudflare Workers Builds (not a manual `wrangler deploy`): root directory `apps/workers/review-worker`, production branch `main`, build command `cd ../../.. && bun install`, deploy command `bunx wrangler deploy`. The Worker name must match that wrangler file or the Git build fails. It runs GLM 5.3-flash via the Workers AI `AI` binding on the manifest + repo content at tag `v<version>` — the manifest's declared `files[]` payload files are extracted from the codeload tarball (`extractPayloadSources`) and fed to the reviewer in full as a PAYLOAD FILES section, since they are the plugin's primary execution surface. pass → `approved`, `latest_version` moves, release tarball (25 MB cap) stored in R2 (`RELEASES`, bucket `open-bot-marketplace-releases`) with sha256 in D1. concern → that version is rejected (a newer version does not hide an already approved listing); `security-bot` comment + GitHub issue on the plugin repo. error → stays `pending`. A newer `enqueuedAt` wins. Loopback publish reviews inline. Every publish re-reviews. Ops: `wrangler queues create open-bot-marketplace-security` (+ `-dlq`), migration `0004_security_review_queue.sql`, `GITHUB_TOKEN` on the consumer Worker, then Pages redeploy so the producer binding exists.
- Marketplace accounts + API keys (migration `0003_marketplace_auth.sql`): users sign in at https://market.open-bot.app (custom domain, active on the Pages project) via openauthster — issuer project `__open_bot_18f8d590` at `https://ef328c08c4d04075a0fd1e7f175983de-auth.webcreas.com` (public PKCE client, no secret needed; vars `OPENAUTH_ISSUER_URL`/`OPENAUTH_CLIENT_ID` in wrangler.jsonc). Account page creates keys (`obm_…`, sha256-hashed in D1, shown once). Paste the key on the dashboard Plugins page ("Marketplace account", admin) → stored in `app_settings.marketplace_api_key`; `marketplace()` in `apps/control/src/plugins.ts` prefers it over the `OPEN_BOT_MARKETPLACE_TOKEN` env fallback. `POST /api/publish` accepts either the instance token or a user API key.
- Manifest or DB changes need `bun run db:generate` for new tables and an image rebuild + desktop restart (`bun run images && bun run update -- --dev`) before existing desktops see new seed skills/CLIs.
