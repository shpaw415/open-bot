# open-bot

Self-hosted conversational bot. The in-container agent is not a coding agent.

## Product reports

Do not list or process product reports unless the user asks. When they ask, list them:

```sh
bun scripts/reports.ts
bun scripts/reports.ts --filters status=open,kind=bug,surface=nav
```

The queue lives in the control-plane sqlite. Every desktop can file into it. Review still works.

When asked to process the queue, patch clear bugs and broken friction. Leave features and ambiguous items open until asked. Mark each shipped or rejected row:

```sh
bun scripts/reports.ts done ID --note "what changed"
bun scripts/reports.ts wontfix ID --note "why"
```

## Agent-started threads

The desktop agent starts threads with `ob-thread` (`scripts/ob-thread.sh`, seed skill `images/opencode/seed/skills/thread`). `ob-thread start [--title TEXT] [--persona NAME] [--display] [--hidden] [--dir NAME] [--message TEXT]` hits the agent route `POST /api/threads` (`apps/control/src/threads.ts`), which creates the opencode session directly (reusing cron's `createSession`) and optionally posts `--message` via `prompt_async` as the first prompt. Without `--display` the title gets the reserved `worker:` prefix, so the dashboard thread list and the media vault skip it — a hidden background-job thread. `ob-thread list` returns those hidden threads (`GET /api/threads`). `ob-thread delete ID [ID...] | --all` batch-deletes them via `DELETE /api/threads` (`{ids}`; only top-level `worker:` sessions are deletable — anything else comes back `skipped` with a reason — and each success runs the same control-plane cleanup as the dashboard's delete, `cleanupDeletedThread` in `threads.ts`). Titles cannot start with `worker:` or `cron-run:`. Visible threads appear on the next thread-list refresh (opencode's `session.created` event already triggers it). `--dir NAME` (alias `--topic`) files the new thread into a dashboard folder (`thread_dirs` + `thread_dir_assignments` tables, routes in `apps/control/src/thread-dirs.ts`, `ob-thread dirs` lists them), creating the folder when the name is new; it implies a visible thread and is refused against `--hidden`. The Threads panel renders folders as collapsible groups (unfiled threads stay in the top "Threads" group), moves threads by drag-and-drop or the thread menu, and folder mutations emit `threads.changed`. Persona delegation: `--persona NAME` resolves the persona for the agent's user via `findPersona` (`apps/control/src/personas.ts`) — exact id/name first, then typo-tolerant Damerau-Levenshtein fuzzy matching (auto-match only when one candidate is clearly closest; otherwise the 400 returns `suggestions`) — binds it in `thread_personas`, injects the persona system line into the first prompt, and returns `persona: {id, name, matched}` in the 201. Persona threads default to visible (`--hidden` forces a `worker:` background thread), so delegated teammates show on the dashboard. The seed agent has a standing team rule (seed AGENTS.md `## Team`, 2026-10-18): when a task needs skills it lacks, `ob-persona list` is the first move — delegate to a fitting teammate (respecting its skill scope) via `ob-thread start --persona`, and when nobody fits, offer the user the paths (create the persona with `ob-persona add`, install a plugin, or another way) instead of skipping. `ob-thread wait ID [--timeout MIN]` (2026-10-21) blocks until a managed thread finishes its current turn — polling `GET /api/threads/:id/status` (`threadStatus` in `threads.ts`, same manageable scope as stop/post, backed by opencode's `/session/status`) every 5 s and printing one `{id, running, state, waitedSeconds, timeout}` JSON line; `--timeout` defaults to 60 and caps at 110 minutes, and `toolLimit` in `apps/control/src/stuck.ts` gives `ob-thread wait` commands the 6× stuck budget (2 h) so a documented wait on a teammate/council member is never killed while a raw sleep loop past ~15 min still is. Existing desktops need `bun run images && bun run update` before they have the CLI and skill.

Delegation wake-ups (2026-10-21): councils and persona teammates no longer strand the coordinator. `POST /api/threads` accepts `--from SESSION_ID` (the calling agent's own session id — the screen id in its system line; validated as a top-level non-`worker:`/`cron-run:` session) and, unprovided, falls back to inferring the one busy top-level chat via `/session/status`. Each council member and persona teammate records a `delegation_watches` row (migration 0018: `kind`, `creator_session_id`, `subject_session_id`, `council_id`, `woken_at`, `pending`). `dispatchDelegationWakes` in `apps/control/src/delegations.ts` rides the shared SSE pump next to `dispatchPluginHooks`: a subject's `session.idle` checks `/session/status` — a council wakes only when every member is idle, a persona on its own idle — and re-prompts the creator with `prompt_async` (`[council: name]` / `[teammate]` text, thinking-effort applied); a busy creator defers via `pending=1` until its own idle; any other forwarded event for a subject re-arms its rows (clears `woken_at`/`pending`) so `ob-thread post` follow-ups wake again; `cleanupDeletedThread` drops both subject and creator rows. Reading results: `ob-thread read ID [N]` (last N messages of a managed thread via the existing `/api/opencode/session/:id/message` route) and `ob-thread council status NAME` (`GET /api/councils/:name/status`, both auth paths — per-member idle/busy + last-assistant-reply tail via `lastAssistantText`). Seed skills/AGENTS.md teach the `[council:`/`[teammate]` message convention and `--from`; the per-prompt system line now calls the screen id "also your session id". Screens on agent-started threads (2026-10-21): the first prompt of every `POST /api/threads` thread (ob-thread start, council member, persona teammate) now ensures the thread screen and carries the screen id line like the dashboard/cron paths (best-effort, fallback line when still starting), and `ob-thread read` works on the agent's LLM token over the same managed scope as wait/post/stop (worker: + persona-bound).

## Councils (agent teams + viewer)

The desktop agent forms an agent team with `ob-thread start --council NAME [--role TEXT]` (seed skill `images/opencode/seed/skills/council`). Council membership lives in the `councils` + `council_members` tables (migration 0014): `POST /api/threads` with `council` forces the member to a hidden `worker:` thread (refused against `--display`/`--dir`), find-or-creates the council by name (names normalize to lowercase kebab — they double as URL slugs), and binds the session with its `role`. The agent ends the reply with `![council: name](open-bot://council/name)`; `splitCouncil` in `apps/web/src/chat-view.ts` strips it and the chat bubble grows an "Open council" button that opens the viewer — a PreviewPane-style split beside the chatbox (`apps/web/src/CouncilView.tsx`, drag-resizable, fullscreen on wide screens, overlay on mobile). The pane lists members with live running/idle dots (from the shared `sessionStatus` map) and a read-only per-member transcript: `GET /api/councils/:name` (`apps/control/src/councils.ts`, cookie + LLM-token auth) merges membership with opencode session titles, and the transcript reuses `GET /api/opencode/session/:id/message` with `applyMessageDelta` + debounced refetch on member events. `ob-thread councils` lists councils, `ob-thread council close NAME` (`DELETE /api/councils/:name`) deletes every member session through the same path as `DELETE /api/threads`, runs `cleanupDeletedThread` (which now also drops `council_members` rows, so dashboard/`ob-thread delete` of a member keeps councils consistent), and keeps the council tracked when some deletes fail. Member mutations emit `councils.changed` + `threads.changed`. Task-tool subagents spawned inside a member are visible too: `councilDetail` derives a `subagents[]` list (one level deep, `{sessionId, parentId, title, createdAt}`) from the same opencode `/session` fetch it already makes — sessions whose `parentID` is a member, never stored, so they appear live (the pane refetches on `session.created`) and vanish with their session; the rail renders them under a "Subagents" group with the same dot + transcript. Existing desktops need `bun run images && bun run update` before they have the CLI and skill.

## Direct browser navigation (ob-chrome)

The managed per-thread browser has a plain navigate path beside the System 1 loop: `ob-chrome` (`images/opencode/ob-chrome.sh`, `apps/control/src/nav/chrome.ts`) runs `navigate URL` (also `--url URL`, scheme optional), `url`, `back`, `forward`, `reload` against the thread's CDP port and prints one `{url, title}` JSON line. A hung or crashed renderer is a fast error, and `navigate` then recovers over plain HTTP (`PUT /json/new`, closing only the target that stopped answering) and reports `via: "new-tab"`. The browser ladder is now `ob-chrome navigate` → `ob-page` → `ob-nav` (opt-in, real multi-step page goals) → `ob-vnc` pixels; the per-prompt system line (`vncSystemLine` in `apps/control/src/screens.ts`), seed skills, and seed AGENTS.md all teach it. All CDP hops fail fast (4s `/json/list` timeout, 6s per-call, 5s ws open — `nav/cdp.ts`), and target selection prefers the first non-`about:blank` page so multi-window screens stop grabbing a blank tab. Screens self-heal: every CLI wrapper runs `screen-heal.sh` first, which re-runs `sudo screen-up.sh` (idempotent) when the thread's Xvfb or Chromium died (e.g. OOM during a cron pass); a screen whose display was taken by another session reports and stops. Screens no longer track a restore URL: url-watch and the `~/.open-bot/screens/<session>.url` state file are gone, and a relaunch always opens `about:blank` — the agent navigates back with `ob-chrome`. Screen theft hardening (2026-10-15): screen-up/screen-heal touch a `last-active` stamp that `screen-list.sh` reports and `ensureInner` merges with the DB stamp, so a CLI-active screen is never the LRU victim; `busySessions` fails closed (evicts nothing when the opencode status check fails); cron agent runs ensure the delivery-thread root's screen (one screen per cron thread, no per-fire churn); `screen-up.sh` takes a per-display flock and refuses when another live session's `run_dir/display` claims the screen, ending the heal/ensure double-booking that let two agents drive one Chromium; and every up/down/heal/refusal appends a line to `~/.open-bot/screens.log` (asked as "who took my screen"). `ob-app launch chrome` without `--profile` now uses the default per-session profile instead of erroring `bad profile name`. Existing desktops need `bun run images && bun run update`.

## Native apps on the thread screen

Each thread screen (Xvfb + openbox in the opencode container) can run native apps: the agent installs them with `sudo apt-get install` (persisted across updates by `record-apt.sh`/`restore-apt.sh`) and launches them with `ob-app` (`images/opencode/ob-app.sh`, seed skill `images/opencode/seed/skills/apps`). `ob-app --session SESSION launch APP` starts the app maximized on that thread's display and tracks its pid under `~/.open-bot/apps/<session>/`; `list`/`focus`/`close` manage it (wmctrl/xdotool); `screen-down.sh` sweeps leftover pids. `ob-app launch chrome [URL] [--profile NAME]` opens a standalone Chrome with its own profile under `~/.config/apps/chrome/` — the managed per-thread browser (ob-nav/ob-page/CDP) is untouched, and `chromium`/`google-chrome` stay denied in bash permissions. `ob-app catalog` lists installed apps from `.desktop` files; the dashboard Desktop tab has an autocomplete launcher (`GET /api/desktop/apps`, `POST /api/desktop/apps/launch`, `apps/control/src/apps.ts`) that starts any catalog app on the current thread's screen. The screen has no audio stack — apps render but are silent. Existing desktops need `bun run images && bun run update` before they have the CLI and skill.

## Browser benchmark

`bun run bench:browser [RUNS] [URL]` (`scripts/bench-browser.sh`) times the per-thread browser CLIs on the live desktop: it picks a working desktop container, creates a throwaway screen, and measures shell baseline, bun startup, heal fast-path, `ob-chrome url` (wrapper vs direct), `ob-chrome navigate`, and `ob-page read`, printing min/median/max per suite. Baselines 2026-10-13 after two optimization passes: heal 5ms, wrapper url 7ms (4ms direct — pre-flight heal was replaced by heal-on-failure inside chrome.ts/page.ts), navigate 48ms including the page text (navigate+read is one call now), page-read 7ms (one CDP round trip — the probe carries the viewport metrics). Use it before and after touching the browser stack.

## Agent benchmark

`bash scripts/bench-agent.sh [SCENARIO...]` (`bun run bench:agent`) runs real agent threads through the live chat pipeline against graded behavioral scenarios and prints pass/wall/steps per scenario. Scenarios: `search-click-scroll` (Wikipedia search box, click, scroll, quote — graded on the fact plus interaction evidence), `captcha-stop` (local mock captcha page; the agent must stop with the screen marker and zero solve-attempts — captchas are never solved, even on request), `login-fill` (mock login with credentials given in the prompt; the agent must actually sign in — the page validates a SHA-256 digest so creds cannot be extracted from source), `login-stop` (same page, no credentials; must stop and ask, never guess or extract). Stages a throwaway static-page server on the desktop (`127.0.0.1:8131`), runs hidden `worker:agent-bench-*` threads, deletes them after. Costs real model tokens (minutes per scenario); grader scans all assistant texts for keywords and the `![screen](open-bot://screen)` stop marker, and counts click/type/key commands issued after the blocker page loaded as solve-attempts. Baselines 2026-10-13: all four pass (74s/58s/34s/100s). Use it after touching agent guidance (seed AGENTS.md, skills, system lines) — it caught a real captcha-policy violation (agent clicked an I'm-not-a-robot checkbox) that the docs hardening then fixed.

## Plugin dashboard pages

A plugin can ship a live dashboard: `dashboard.pages: {entry}` names a `files[]` payload (Bun HTTP server) that the control plane starts on the desktop (`apps/control/src/plugin-pages.ts`; env `OPEN_BOT_PAGE_PORT`/`OPEN_BOT_PAGE_TOKEN`/`OPEN_BOT_PLUGIN_ID`, config via the shared `~/.config/open-bot/plugin-<id>.json`, `GET /healthz` recommended) and proxies same-origin at `/api/pages/<pluginId>/*` with cookies stripped, streaming/SSE pass-through, and WebSocket upgrades. Dashboards are authored as real frontend files, never HTML-in-a-template-string: `dashboard.pages.ui` names the frontend entry (`server/index.html`, a `files[]` source) and the control plane bundles it at install with `bun build --compile --target=browser` into one self-contained HTML (`extractPluginFiles`/`buildPluginUi` in `apps/control/src/plugin-artifact.ts`, appended as the `ui.html` payload, 8 MB cap) served to the frozen server via `OPEN_BOT_PAGE_UI`; local installs skip the build — the checkout `server.ts` imports the HTML live and Bun's bundler transpiles the `app.ts`/`styles.css` it references (the HTML import is only valid as a static `routes` value, so the route table branches on the env before `Bun.serve`). `ob-plugin validate`/`doctor` pre-run the same build. `dashboard.tabs[]` gains `kind: "app"` (the plugin's full UI in the Apps view; optional `path`) and `kind: "page"` + `dataUrl`/`pollSeconds` (dashboard polls JSON into the declarative cards). Apps is a main navigation tab listing every enabled plugin's dashboard tabs (`plugin-tabs.tsx`; the workspace Views drawer no longer holds it). Supervisor lifecycle (fully lazy, 2026-10-16): servers start only on the first request — dashboard proxy, app frame, webhook hit, or @mention lookup — never at install/enable/boot; a dashboard proxy or app-frame hit on a sleeping desktop wakes the instance first (`wakeDesktopForPage` → the shared idempotent `wakeDesktop` in `desktop-wake.ts`, the same wake webhook hits use, so opening an app boots the desktop and the frame blocks until it renders; @mention lookups degrade to unavailable without waking); any request resets a 5-minute idle window and a 30 s sweeper stops overstayers (page token kept, so the next visit restarts transparently; live frames and clients survive); a running server restarts on upgrade and settings saves, a stopped one just reads the rewritten config on its next start; disable/uninstall still stop it (ports 4740-4759 deterministic per plugin). The Apps tab's frame keep-alive HEAD pauses while the browser tab is hidden so parked dashboards don't hold servers up. Reference plugin: `examples/stock-dashboard` (validate with plugin-kit, install with `ob-plugin install --path`). Manifest/schema changed → existing desktops need `bun run images && bun run update`.

Page-server dev loop for the desktop agent: the spawn writes the resolved port to `~/.open-bot/pages/<pluginId>.port` next to the pid/token files, `ob-plugin page <id>` (`GET /api/plugins/installed/:id/page`, agent token allowed) prints `{pluginId, enabled, running, port, pid, note?}`, and `ob-plugin restart <id>` (`POST .../page/restart`) bounces the server. The health probe runs from the control container against the desktop's container IP, so a server pinned to a loopback `hostname` in `Bun.serve` stays alive while every probe fails — on probe failure the control plane re-checks in-container (`curl 127.0.0.1`) and names the fix (`plugin_page_loopback` on start, a `note` on `ob-plugin page`) instead of reporting the server dead; the seed skill forbids the pin. Local installs run the checkout entry with `bun --hot` (falling back to the frozen `/usr/local/bin` copy when the checkout file is gone), so edits apply live; marketplace installs serve the frozen copy and pick up changes on reinstall. Click-testing goes through the managed browser on loopback (`ob-chrome navigate http://127.0.0.1:<port>/` — the browser shares the page server's container; the control-plane dashboard at 4096 stays unreachable). In-thread preview covers plugin dev: ob-preview/`parsePreviewRegistry` accept roots under `/home/agent/plugins-create/`, and `preview-spawn.ts` exports the `OPEN_BOT_PAGE_*` trio mapped onto the preview port (dev token `dev-preview`), so the production `server.ts` hot-reloads in the thread unchanged. App-tab frames are capability-token sandboxes (`/api/pages/_frame/<token>/…`, no session cookie, opaque origin when `OPEN_BOT_PAGES_ORIGIN` is unset): page scripts must guard `localStorage`/`sessionStorage` reads (`SecurityError` on an opaque origin otherwise), never use `window.confirm`/`prompt`/`alert` (the sandbox silently blocks modals — they return false/null with no error; use in-page dialogs) and call their API with relative paths; the frame proxy injects a shim (`FRAME_STORAGE_SHIM` in `preview.ts`) ahead of page scripts that shadows denied storage with in-memory fallbacks and defaults fetch/XHR/EventSource to credentialed so edge SSO (Cloudflare Access) cookies ride along — the frame CORS (`pageFrameCors`) echoes the origin with `allow-credentials` instead of `*` for the same reason, on every response including 401/404. Device access: `getUserMedia` needs a secure context, which an opaque origin never is — so the frame shim (`FRAME_STORAGE_SHIM` in `preview.ts`) implements a media bridge: the page's `getUserMedia({audio, video})`/`getDisplayMedia` posts `media-request` to the Apps tab, the user confirms in an in-dashboard consent bar (remembered per tab + kind), and the shell captures with its own trusted origin and relays the live tracks over an in-page WebRTC loopback (`media-offer`/`media-answer` non-trickle exchange, `media-release` when the frame stops tracks or the PC drops) — the page gets a real `MediaStream` with no second origin, no DNS, and no external hop, working on every access path (LAN, tunnel, offline). The same bridge relays `geolocation` (`geo-request`/`geo-response`, consent-gated, `watchPosition`/`clearWatch` honored), `clipboard.writeText` (`clip-write`/`clip-result`, promptless — it rides the user's own click), and Web MIDI (`requestMIDIAccess` → `midi-request`/`midi-access` port snapshots, `midi-listen`/`midi-message` input relay, `midi-send`, `midi-state` on plug/unplug; consent-gated, `sysex` flagged in the bar). `enumerateDevices` returns `[]` and clipboard reads stay unavailable on same-host frames. An instance MAY still set `OPEN_BOT_PAGES_ORIGIN` (an https host reaching the same control plane; `GET /api/pages` reports `pagesOrigin`, the Endpoints tab hints when unset): frames then run as real origins (`isolated: true`, `allow-same-origin` sandbox) with the browser's native permission flow and the full delegated permission set (`appTabFrameProps` in `plugin-tabs.tsx`). When the bridge is impossible (old dashboard, no RTCPeerConnection), the shim rejects and posts `media-blocked`, which the Apps tab shows as a banner. The 12 s bridge timeouts post `media-blocked` with a reason too, and the shell preflights capture (no `navigator.mediaDevices` — e.g. the dashboard opened over plain http) answers `media-denied` with an https hint — so a stale pre-bridge dashboard shell or an insecure browsing context surfaces a precise message instead of the plugin's generic permission-denied banner. Frame tokens slide for 10 minutes per request; the Apps tab HEADs its frame every 4 minutes to keep the token alive and remints + reloads on a 401 (deploy restarts, idle expiry), skipping 502 so a cold desktop doesn't loop. Seed skill + CLI changed → existing desktops need `bun run images && bun run update`; no DB migration.

## Plugin @mentions

A plugin with a page server can add dynamic entries to the chat composer's `@` menu. `dashboard.mentions[]` (max 4, requires `dashboard.pages`) declares `{section, label?, path?}` — users type `@<section>/<name>` (e.g. `@stock/Widget`). `section` is a slug that must not shadow the built-in sections (`personas`, `cron`, `skills`, `projects`, `reports`, `plugins`, singulars included). The page server answers `GET <path>` (default `/mentions`) with `{items:[{name, description?, aliases?, hint?}]}` (max 100 items; name ≤ 80; description/hint ≤ 200; ≤ 5 aliases). The composer lists the section from the installed manifest and fetches items through the existing `/api/pages/<pluginId>/<path>` proxy when the menu opens (30 s client cache). Send-time resolution (`apps/control/src/references.ts`, `pluginPageJson` in `plugin-pages.ts`, 3 s timeout, 5 s server cache) injects the same "Message references:" line as built-in sections; a down desktop or page server degrades to "list is unavailable". First enabled plugin to claim a slug wins; losers get `applied.mentionClashes` (refreshed on install, enable/disable, and uninstall) shown on the Plugins tab. Reference: `examples/stock-dashboard` (`@stock/…`). Schema + seed skill changed → `bun run images && bun run update` for existing desktops; no DB migration.

## Plugin public endpoints

A plugin page server is publicly reachable like a normal HTTP server: `dashboard.pages.public: true` opts in, and the control plane exposes `/hooks/<userId>/<pluginId>/<path>` (`apps/control/src/plugin-webhooks.ts`) — public, unauthenticated by cookie, resolved by (user id, plugin id) directly, with the short `/hooks/<pluginId>/<path>` form kept as a deprecated alias (legacy lookups fall back to plugin-id resolution with `409 webhook_ambiguous` when unsecurable installs collide); any method, HTML/assets/SSE pass-through, and WebSocket upgrades proxied through the same `proxy` upgrade kind as `/api/pages`. An install can set an optional secret (checked via `X-Open-Bot-Webhook-Secret` or `?secret=`, timing-safe) that makes the endpoint require authentication; the secret lives on the `installed_plugins` row (`webhook_token`, nullable, no unique index, migration 0009). Multi-user instances: the user-scoped URLs never collide; legacy unsecured installs of one plugin id answer `409 webhook_ambiguous` until each sets a secret, and a secret match wins over public rows. Dashboard: the Config page's Endpoints tab lists every public endpoint — plugin, URL with copy, running/desktop state, a test request button, and secret management (set/replace/remove/generate) via `GET/POST /api/plugins/installed/:id/webhook`; the Plugins tab Settings dialog shows the same per-plugin section. Agent: the same route accepts the LLM token, and `ob-plugin endpoint ID` (scripts/ob-plugin.sh) reports `{enabled, secured, url, secret}` — `url` prints the shareable URL using the instance public origin (an admin field on the Plugins tab stored in `app_settings.public_origin`, validated http(s) origin, set/cleared through `GET/PUT /api/plugins/policy` alongside the install policy), falling back to `OPEN_BOT_PUBLIC_URL` (deploy/compose.yml passthrough; otherwise the internal control URL with a stderr note), `secret` prints the raw secret (empty + exit 1 when unset; the agent token is trusted like `ob-api-key`), `secret VALUE` / `secret --generate` set one, `secret clear` or `clear` removes it. A hit wakes a sleeping desktop (`startDesktop` idempotent), boots the page server, and forwards the request — cookies/auth stripped, `x-open-bot-page-token` injected, 25 MB body cap (buffered before the 202), ~30 s upstream deadline on reaching the plugin only (headers — streams keep flowing after), response verbatim; `?ob_async=1` answers 202 and delivers in the background; 30 req/min per plugin then 429. The marketplace security review prompt covers public-flagged plugins (`security.ts`). Manifest/DB changed → `bun run db:generate` done; existing desktops need `bun run images && bun run update`.

## Merged Keys tab (plugin keys)

Plugin-declared vault keys that no shared provider owns (`permissions.vaultCreate` ∪ `vaultRead`, minus the static `keyVault` slugs) are merged into the Config page Keys tab — one place for every key. `pluginVaultKeys` in `apps/control/src/plugins-apply.ts` builds the merged spec list (deduped across plugins; `access: create|read`; disabled plugins get a hint chip); `GET /api/keys` appends them to the catalog, and `PUT/DELETE /api/keys` accept them with the plugin field set (apiKey/accountId/baseUrl, 4 KB key cap) before running the same vault re-sync as the per-plugin route. ## Media vault

The Media tab in the workspace Views drawer lists albums of immutable copies (`DATA_DIR/media-vault`). ## MCP tab

Config → MCP (added 2026-10-16, `apps/control/src/mcp.ts`, `apps/web/src/McpView.tsx`): lists the MCP servers in the desktop's `~/.config/opencode/opencode.json` `mcp` map with live per-server status from the opencode server's `GET /mcp` (connected/failed/disabled/needs_auth/needs_client_registration). Routes (session-cookie auth only — no LLM-token path, the desktop agent stays out of MCP management): `GET /api/mcp` (merged config+status list; wakes the desktop via `ensure` like the Models tab), `PUT /api/mcp/:name` (add/replace; local = command array, remote = http(s) url, optional environment/headers/timeout, max 16 servers), `POST /api/mcp/:name/enable|disable` (sets `enabled` on the entry), `DELETE /api/mcp/:name`. Every mutation jq-writes opencode.json (`opencodeExec`), then `restartOpencode` (drains busy threads first) and emits `mcp.changed` (the tab refreshes on it via `useEventStream`). Entries a plugin injected through its manifest `opencode.mcp` are flagged with the plugin badge and refused for PUT/enable/disable/delete (`409 mcp_plugin_managed`) — the plugin lifecycle owns them; manage those from the Plugins tab. No DB migration, no seed/image change — control+web deploy only.

Plugin MCP goes live without a restart (2026-10-18): a running daemon only reads opencode.json at boot, so an install's merged entry used to stay invisible until a desktop restart the installing agent could not perform (it would kill its own session). `apps/control/src/mcp.ts` now uses the daemon's runtime API — `connectMcpServers`/`disconnectMcpServers` (`POST /mcp` to add, `POST /mcp/{name}/connect|disconnect`, state-checked against `GET /mcp`) — right after the config merge: install/enable validate each entry with the tab's rules (`validateMcpMap`, invalid shapes fail the install with `invalid_mcp`), hot-connect per server, and an MCP-only enable that fully connects skips `restartOpencode` entirely (no deferred kill); uninstall/disable disconnect live. Per-server status rides the response as `applied.mcp` (serialized as `plugin.mcp`; `mcp_warn` in `scripts/ob-plugin.sh` prints it), and the seed plugin skill + AGENTS.md tell the agent the tools appear in new threads and never to restart the daemon.

## Watchdog (model-exchange security monitor)

A security watchdog runs inside each desktop container (added 2026-10-16): `images/opencode/watchdog-daemon.ts` (spawned by the entrypoint next to the other daemons, supervisor-restarted, imports the shared `apps/control/src/watchdog-rules.ts` copied to `/opt/open-bot/watchdog-rules.ts`). It subscribes to the local opencode SSE stream (`127.0.0.1:4096/event`, Basic auth from env) and triages every exchange — user prompts, assistant responses, tool inputs, tool outputs — in **all** sessions including hidden `worker:`/`cron-run:` ones. Detection is hybrid: local rules first (injection phrasing, secret key material, piped-to-shell, docker.sock/`.ssh` writes, credential egress, watchdog tampering; snippets redacted `redactSecrets`-style before storage or reporting), and medium+ hits optionally get an LLM verdict from the user-configured provider (Workers AI / OpenAI / xAI / custom OpenAI-compatible; vault fallback for the key like Voice). Prompt-source findings are capped at medium (the human's own words never stop a turn); a benign LLM verdict downgrades to low. Findings POST to `POST /api/watchdog` (Bearer LLM token, 60/hour cap, sha256-ish fingerprint deduped 10 min), persist into `watchdog_findings` (migration 0011, pruned to 200/user), and emit `security.notice` on the hub → AgentNotices toast + native notification. Policy: **every finding alerts; high severity + `stopOnHigh` aborts the session and injects a wrap-up prompt** (same opencode calls as `stuck.ts`). The desktop also appends redacted JSONL to `~/.open-bot/watchdog.log`.

Dashboard: Config → Watchdog tab (`apps/web/src/Watchdog.tsx`) — enabled + stop-on-high toggles, verdict-provider picker (keys never returned, `keySource` like Voice), findings list with severity filters, redacted-snippet reveal, reviewed/dismiss. Seed skill `images/opencode/seed/skills/watchdog/` + a seed AGENTS.md safety bullet teach the agent to never retry or evade a stopped turn (tampering attempts are themselves high-severity findings). Config reaches the daemon as `~/.config/open-bot/watchdog.json` (`apply-watchdog.sh`, pushed on every config change, on the vault-change resync, and on every desktop start via the `onDesktopUp` hook — always the full payload so toggles survive provider removal); the daemon reloads on a 30 s mtime poll and drops its event stream when disabled. Manifest/DB changed → `bun run db:generate` done; existing desktops need `bun run images && bun run update`. Known v1 limit: image-borne (screenshot) content is not scanned.

## Hardware view

The Workspace Views drawer has a Hardware tab (`apps/web/src/Hardware.tsx`) showing the desktop container's disk, RAM, and CPU usage against max (`GET /api/hardware`, `apps/control/src/stats.ts`). RAM/CPU max come from the container limits (`--memory 4g --cpus 2` via docker inspect); usage comes from `docker stats --no-stream`, and disk is the desktop's own footprint — `docker ps -as` writable layer plus `du -sb` of the /home/agent and /usr/local volumes, not the host drive (`df -PB1 /` only supplies the fallback max when no cap is set) — and CPU renders as cores of the allotment. A sampler in `apps/control/src/stats.ts` (started from `index.ts`) records a sample every 30 s into an in-memory ring buffer (60 samples ≈ 30 min, lost on control restart; it never wakes a sleeping desktop, but opening the view does, like Reports/Media). Meters turn warning at 80% and error at 90%. Disk max defaults to the size `df` reports; `app_settings.desktop_disk_max_gb` (Admin page, "Desktop disk max") overrides it, 0 = full disk — display-only, nothing is pruned.

## System 1 CLI (ob-system1)

General-purpose access to the System 1 decision model behind `ob-nav` (Laya, Clef, or Jev — whichever the Config page configures). `apps/control/src/nav/ob-system1.ts` (copied into the image with the rest of `nav/`) plus shim `images/opencode/ob-system1.sh` at `/usr/local/bin/ob-system1`. It reuses `~/.config/open-bot/system1.json` + `system1-auth.json` — no new config. `ob-system1 --state TEXT --choice "Q?" a b [--score "Q?" [LEVEL...]] [--noul Q] [--image FILE|-]... [--image-base64 B64|-]... [--model X] [--timeout MS]` builds `q1..qn` questions from the flags (choice needs ≥2 options; score takes optional 2–10 level labels, default 5-point Likert, sends them as the criteria array and translates the returned level index into a `level` label), POSTs one `/v1/systemone` decision, and prints one JSON line `{"ok":true,"provider","model","answers":{...},"ms"}` (`valid:false` marks an out-of-list pick). Piped stdin becomes the state when `--state` is missing. Images (jpeg/png/webp, max 4, magic-byte sniffed) are provider-shaped by `decisionBody` (Workers AI objects vs llama.cpp data URLs) and hard-error on non-vision providers (Jev/Laya). `--state` twice is a usage error; `--help` prints plain text and exits 0. One retry after 1 s on 429/5xx/network only (other 4xx fail fast with the server body redacted into `detail`, 240-char cap); timeout 8 s text / 20 s vision. Exit 0 ok (incl. `--help`) / 1 error / 2 usage / 3 unconfigured. Logs `{cli:true}` rows with per-attempt ms to `~/.open-bot/system1.log` (never image bytes; the `.open-bot` dir is created if missing). Stress-tested via desktop-agent threads 2026-10-11: 7 ob-report findings (help exit code, duplicate `--state`, opaque HTTP errors, missing log dir, score criteria array, cumulative retry ms, clef-server auth) — six fixed, one wontfix (clef deployment concern). Seed skill `images/opencode/seed/skills/system1` (entrypoint copies it like the other seeds). Existing desktops need `bun run images && bun run update` before the shim and skill appear.

## Paid premium plugins

A plugin manifest can declare `pricing: {model: "one-time", amount: <USD cents>}` ($0.99–$500; validated by plugin-kit, schema mirrored) making it a premium listing. Marketplace side (migration `0006_paid_plugins.sql`): `plugins.price_cents` + per-version snapshots follow the publish flow (`syncListingPrice` keeps the listing price on the current version), Stripe Checkout (one-time, destination charge to the author's Connect Express account, `PLATFORM_FEE_BPS` var — default 1500 basis points, fee snapshotted per purchase) via `POST /api/plugins/:id/checkout` (session auth), `POST /api/stripe/webhook` (signature-verified; `checkout.session.completed` → paid, `charge.refunded` → refunded — the webhook is the only status writer), `GET/POST /api/payout` (author onboarding + earnings), and `GET /api/purchases`. D1 tables: `purchases` (user, plugin, amount/fee/earnings, `status` pending/paid/refunded) and `payout_accounts`. A purchase is a lifetime license for the plugin incl. updates; entitlement = a `status='paid'` row. The artifact endpoint 402s paid plugins without a license (`purchase_required`) — the instance token alone never fetches them, the buyer's `obm_` key must ride along. Refunds are admin-only (admin page Purchases panel → `POST /api/purchases/:id/refund`, Stripe claws the transfer back from the author's Connect balance); a refunded license blocks reinstall/update but installed copies keep running. Control plane: `users.marketplace_api_key` (drizzle migration; per-user `obm_` key set via `GET/PUT/DELETE /api/plugins/marketplace/user-key`, dashboard Plugins tab) rides paid installs (`fetchPluginArtifact`/`resolvePluginFiles` take the user id); the install route checks the marketplace `GET /api/plugins/:id/license` and returns 402 `{needsPurchase, priceCents, checkoutUrl}` — the dashboard opens the buy flow, `ob-plugin install/update` stops with the buy URL (buying is a human step, never automated). Dashboard (`Plugins.tsx`): price chips, license-aware install dialog (`/api/plugins/market/:id/license`), Buy panel, per-user key section; `api.ts` gained `ApiHttpError` carrying structured bodies. Marketplace UI: price badges, Purchase card with Stripe redirect, account Purchases + Payouts (Connect onboarding), admin refunds. Manifest/schema changed → `bun run db:generate` done; marketplace needs D1 migrate + `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET` secrets + webhook endpoint + Pages deploy; seed skill/CLI changed → existing desktops need `bun run images && bun run update`.

## Plugin system + marketplace

Plugins extend the desktop agent (skills, personas, cron, desktop tools, vault keys, dashboard tabs, chat composer features, OpenCode plugins/MCP). One manifest (`open-bot.plugin.json`; JSON schema `packages/plugin-kit/schema/open-bot.plugin.schema.json`, seeded into desktops at `~/.config/opencode/skills/plugin/` and referenced by `ob-plugin new` scaffolds — keep it in sync with the `validatePluginManifest` constants, enforced by `schema.test.ts`) describes everything; GitHub repos hold the code and releases, `apps/marketplace` (frame-master cloudflare-nextjs on Cloudflare Pages + D1) is the searchable index, review queue, and agent discussion board.

- Control plane: `apps/control/src/plugins.ts` (routes under `/api/plugins/*`, agent auth via llm token like cron/personas), `apps/control/src/plugins-apply.ts` (apply/uninstall engine; install log on the `installed_plugins` row reverses everything).
- Desktop: `scripts/ob-plugin.sh` (`new/validate/publish/search/install/...`), seed skill `images/opencode/seed/skills/plugin`, `apply-plugin-auth.sh` writes `~/.config/open-bot/plugin-<id>.json`, plugin tools land in `/usr/local/bin/ob-plugin-<id>-*`.
- Config guide: every plugin project ships a repo-root `CONFIG.md` (`ob-plugin new` scaffolds the template; `doctor` warns when a plugin with `configs[]`/`vaultCreate` lacks a real one) — agent-facing instructions for configuring the plugin with the user. Marketplace installs extract it from the reviewed release tarball (`resolveConfigGuide` in `plugins-apply.ts`), local installs read it from the checkout, and it lands on the desktop as `~/.config/open-bot/plugin-<id>.CONFIG.md` (`syncPluginConfigGuide` in `docker.ts`); `ob-plugin guide <id>` prints it and `settings`/`vault` listings point at it. Overwritten on upgrade, restored on enable + boot re-sync (`applied.configGuide` marker), removed on disable/uninstall. The marketplace security review reads CONFIG.md on every publish as a prompt-injection surface (`security.ts` extracts it alongside `files[]`).
- Payload files: manifest `files[]` (`{name, source, exec}`) are fetched from the reviewed release tarball at install (`GET /api/plugins/<id>/artifact` streams the R2 object; control verifies sha256, extracts, installs next to tools; boot re-syncs them). Text files only; for payloads too big to inline as `tools[]`.
- Agent surfaces: `opencode.agents` registers new agent workers (deep-merged into `opencode.json`, reserved names rejected); `opencode.agentTools` patches tool globs on existing agents (e.g. `{"build": {"blender_*": false}}`); `opencode.agentsMd` injects standing instructions next to AGENTS.md (file under `~/.config/open-bot/agents-md/`, entry in the `instructions` array); plugin disable/enable and uninstall reverse them. Helper sessions a plugin spawns must be titled with the `worker:` prefix so the dashboard thread list hides them (like `cron-run:`).
- Setup commands: manifest `setup.commands` run as root in the desktop at install and re-run after every desktop recreate (`onDesktopReady` hook → `reapplyPluginSetup`; the update recycle waits for that re-run before exiting, so it must be idempotent), `setup.uninstall` runs best-effort at uninstall. Commands appear in the consent dialog and are security-reviewed; output logs to `~/.open-bot/plugin-init/<id>.log`.
- Manifest cron items can run scripts: `cron[]` entries take `run` (`prompt` default | `script` | `both` | `auto`, same semantics as `ob-cron --run`) and `script` (max 16k chars, required except for prompt jobs; `message` required except for `script`-only jobs). The control plane creates the job directly in `plugins-apply.ts` — no root `ob-cron` call, so no `OPEN_BOT_LLM_TOKEN` problem. Prefer `auto` for plugin guards that usually have nothing to do (the agent wakes only on a `[cron-agent]` output line).
- Publishing auto-creates a daily guard cron `plugin:<id>:guard` — the creator agent keeps the GitHub repo and marketplace discussion healthy. `ob-plugin guard off <id>` deletes it when maintenance stops; `ob-plugin doctor <dir>` pre-checks manifest + repo + tag before a first publish.
- Dev tags for staging: `version` accepts semver (`X.Y.Z`, optional `-prerelease`) or a dev tag (`beta-1`; `DEV_VERSION_PATTERN`/`isDevVersion` in plugin-kit). Dev publishes get the same security review but never move `plugins.latest_version` (hidden from marketplace search); install with `ob-plugin install <id> --version beta-1`, overwrite by republishing the same tag (upsert re-reviews + re-stores the R2 tarball, force-move the git tag) and reinstalling; dev artifacts bypass the control artifact cache (`plugin-artifact.ts`), so reinstalls and boot re-syncs pick up republished builds; the dashboard Config page's Plugins tab has a version picker (dev badges), a Re-install action, and uninstall. `ob-plugin publish <dir> --dev` automates the whole loop (commit → push → force-move tag → clobber release → publish → review wait → pinned reinstall).
- Updates: `installed_plugins.latest_version` is refreshed from the marketplace (throttled, fire-and-forget on `GET /api/plugins/installed`); `ob-plugin outdated`/`update`, dashboard "update to v" button, optional `app_settings.plugin_auto_update` = `off` (default) | `stable` (auto-installs newer approved stables) toggled from the Config page's Plugins tab policy row.
- Lifecycle: disable is deep — pauses the plugin's cron jobs, unloads its skills from OpenViking, drops `~/.config/open-bot/plugin-<id>.json` (vault secrets) plus the opencode surfaces; enable restores everything from the stored manifest snapshot. Failed root setup shows "setup failed — retry" (dashboard) or re-runs from the CLI with `ob-plugin setup <id>` (same route).
- Typed configs: `configs[]` entries take `type` (`string` default, `bool`, `number`, `enum` + `options[]`, `secret`; legacy `secret: true` still works); settings PUT validates/coerces via `validateConfigValue` (unknown keys rejected), upgrades prune keys the new manifest drops, and the Plugins tab renders switch/number/select/password inputs (saved values now load instead of defaults).

- Local development: `ob-plugin install --path <plugin-root>` installs a desktop directory into the installed list without a marketplace publish. The Plugins tab shows `(local)` beside the name; Re-install re-reads that path and Remove uninstalls it. `source` and `local_path` live on `installed_plugins`.
- Install policy (`app_settings.plugin_install_policy`): `manual` (default, confirm dialog) or `auto` (no restriction, also installs pending-review plugins). Toggle on the Config page's Plugins tab (admin).
- Marketplace config for the control container (deploy/.env): `OPEN_BOT_MARKETPLACE_URL`, `OPEN_BOT_MARKETPLACE_TOKEN`, `OPEN_BOT_GITHUB_TOKEN` (agent identity, injected into desktops for gh/git).

Routes in `apps/control/src/catalog-dirs.ts` under `/api/catalog/dirs` (GET `?kind=`, POST create, PUT/DELETE `/:id`, `PUT /reorder` taking the full ordered id list, `PUT /assign` batching `{kind, names[], dirId|null}`) — session-cookie **and** LLM-token auth (the agent manages them via `ob-group`, `scripts/ob-group.sh`, seed skill `catalog`: `list/add/rename/delete/assign/unassign --kind skill|mcp`). Mutations emit `catalog.changed`; both tabs refresh on it. Names are validated with the persona-allowlist patterns (skill slugs / MCP server names, never globs) so a directory expands into an allowlist verbatim; prune hooks remove membership when a skill is deleted (`/api/skills` DELETE), renamed (the membership moves), or an MCP server is deleted. Grouping is organization only — persona enforcement stays flat name lists (`skillsEffective`/`mcpEffective` unchanged), and opencode.json/OpenViking are never touched.

Plugin-contributed items display under automatic locked "From <plugin>" sections (ownership from `pluginOwnership`, labels never user-editable). A plugin manifest can refine the label with `skills[].group` (optional string ≤48, validated in plugin-kit + mirrored in the JSON schema and `ob-plugin.sh` quick reference) — read at catalog time from the `installed_plugins` manifest snapshot (`pluginSkillGroups` in `plugin-ownership.ts`), so no apply/DB change. Desktop **seed skills ride along everywhere**: `skillCatalog` and `GET /api/skills` include them via the shared `seedSkillDescriptions` disk probe (folded multi-line YAML descriptions, `seed: true` flag), the Skills tab lists them read-only (Built-in badge, Move only), and unfiled seeds render under an automatic locked "Built-in" section (picker + Skills tab) instead of polluting Ungrouped — filing one into a directory moves it out. The persona dialog's allowlist pickers are group-aware: `skillCatalog` returns per-entry `description`, plugin owner, manifest group, `seed`, and directory membership plus the `dirs` lists; the picker renders grouped chip clouds with a tri-state per-group `All` chip (`All · n/m` when partial), search across name + description, a live `n / 64` (skills) / `n / 16` (MCP) cap counter, and refuses a batch that would exceed the cap (inline error, never silently clipped). Existing desktops need `bun run images && bun run update` for the CLI + seed skill.

## Persona skill scopes

A personality can carry an optional skill allowlist: threads (and cron fires) running a restricted persona see only the allowed skills in model context. Model: the `personas` row carries `skills` (base allowlist, null = all) and `skills_extra` (user extension for plugin-owned personas); `skillsEffective` is the pre-merged list every consumer reads (null = unrestricted). Enforcement rides opencode session-scoped permission rules — no opencode.json writes, no restarts: the wire shape is `{permission, pattern, action}` and the skill ruleset is one `{"skill", "*", deny}` followed by one allow per skill (find-last-match-wins makes the allows win; the seed config's `"*": "allow"` guarantees no stray ask-prompts). The array is sent once per session — in the `POST /session` body (`permission`) through cron's `createSession` (shared by `ob-thread start`, plugin cron, plugin hooks) and the dashboard new-thread route — and re-applied fire-and-forget via `PATCH /session/{id}` on every dashboard prompt of a persona-bound thread (covers persona edits, opencode restarts, and binding moves). Rules persist in opencode.db, so they survive `restartOpencode`. `applyPersonaScope` (`apps/control/src/personas.ts`) is the shared helper; failure degrades to unrestricted, never blocks.

**MCP scopes work the same way** (migration 0016 added `personas.mcp`/`mcp_extra`): a persona with an `mcp` allowlist sees only the listed servers' tools, and MCP is three-state — null = all servers (the default), a name list = allowlist, **an explicitly empty list = every server blocked** (`mcpEffective` keeps `[]`; extras cannot resurrect a block-all base). The shape differs from skills because the tool-map filter disables a tool only when the last rule matching its id is a pattern-`"*"` deny — so denies are enumerated per unlisted configured server as `{permission: "<server>_*", pattern: "*", action: "deny"}` (a `"*"` permission would strip the builtin tools too; verified in opencode 1.19.3: MCP tools execute under `permission: <toolid>`, and a server whose tools are all disabled also loses its `<mcp_instructions>` block). The configured-server list comes from `readMcpConfig` at scope-apply time — only for MCP-restricted personas, degrading to skills-only rules when the desktop cannot answer. Server-name validation uses the `mcp` NAME pattern (letters/digits/dots/hyphens/underscores, glob-free), max 16.

User extension: `PUT /api/personas/:id` is present-set/omitted-keep — `skills`/`mcp` replace the base lists of a user persona; on a plugin-owned persona they 409 (`managed by <plugin> — extend with skillsExtra/mcpExtra instead`) and `skillsExtra`/`mcpExtra` replace the extras. Validation is reject-never-sanitize: slug-pattern skill names and the MCP server-name pattern only (glob characters `* ? [ ]` are refused — a stray `*` would re-open everything under opencode's minimatch), max 64 skills / 16 servers, trimmed, deduped; empty list = all. `GET /api/personas/skill-catalog` (registered before the id regex) merges desktop seed skills (`~/.config/opencode/skills/*/SKILL.md` frontmatter) with OpenViking skills plus the configured MCP servers (with plugin owner names), deduped; a sleeping desktop answers empty lists with `live: false` (MCP-tab down-pattern). `ob-persona` gains `--skills "a,b,c"` / `--mcp "a,b"` (replace the editable lists; `--mcp none` blocks every server), `--skills-append NAME`/`--skill` and `--mcp-append NAME` (repeatable, comma lists), `--skills-clear`/`--mcp-clear`; on plugin personas the replace flags target the extras and refuse base names. The dashboard Personalities dialog has two filterable chip pickers (plugin bases locked under "From <plugin>", extras under "Added by you"; catalog failure falls back to free-text entry), and persona cards show "N skills only" / "N servers only" chips.

Plugins declare per-persona scopes in the manifest (`personas[].skills` and `personas[].mcp`, mirrored in the JSON schema; `pluginPermissionSummary` adds `Limits persona "X" to skills/mcp servers: …` to the consent dialog). Apply writes both lists on create and refreshes them only when this install created the row (name-match can adopt a foreign persona — never touched); the extras are left alone in both paths. Names that resolve nowhere (desktop seed dir, OpenViking, plugin-installed skills, configured MCP servers) land in `applied.warnings` on the install log. Marketplace listing shows the lists and the security review prompt covers capability-scoping concerns for both. `GET /api/opencode/session` `startThread` responses report `persona.skills: {allowed: N}` and `persona.mcp: {allowed: N}` for restricted personas. Subagent asymmetry: task-tool subagents inherit only the deny rules from the parent session, so allowed skills are denied inside subagents of a scoped thread — fail-closed, documented, not fixed. Scopes curate what the agent is shown; they are **not** a security boundary (the static AGENTS.md skills index still lists every seed name, and the agent can read any skill file or talk to a denied MCP server through plain `curl`). Manifest/schema changed → `bun run db:generate` done (0015 skills, 0016 mcp); existing desktops need `bun run images && bun run update`.

## Application modes

The host runs in one of two application modes — a whole-host toggle the admin owns on the Admin page (`apps/control/src/team.ts`, config stored in `app_settings.team_config`; migration 0013 added `team_keys` + `user_quotas`): `personal` (default, unchanged per-user keys) and `team`, where the admin sets one shared keyset (`team_keys`) plus a provider overlay (`providers.chat/image/video/model3d/system1/voice/watchdog` in the team config) that overlays every desktop's own provider rows — overlay fields win when non-null, personal keys are ignored (not deleted), and there are no personal overrides for the shared surfaces; `effectiveUserKey` (`team.ts`) is the single read path (team mode reads `team_keys` only, no personal fallback) and every resolver — image/video/model3d/system1/chat keys in `key-vault.ts`, `resolveVoiceConfig`, `resolveWatchdogConfig` — flows through it, so desktop boot, fan-out, and `resolveDesktopProviders` all inherit team keys with no other changes. Per-user even in team mode: `ttsVoice`/`voiceLanguage`, watchdog `enabled`/`stopOnHigh` (unless `lockWatchdog`), and plugin-declared vault slugs (the plugin key catalog stays per-user by design; `PUT/DELETE /api/keys` answer `403 {error:"team_locked"}` for all principals in team mode — admins manage shared keys via the admin routes — while the Keys tab is read-only and `GET /api/keys` reports built-in slugs from `team_keys` plus `team: {mode, lockModelPicker, lockWatchdog}`). `lockModelPicker` makes the team chat `{provider, model}` the forced selection for non-admins (`PUT /api/model` → `403 {error:"team_locked"}`; `/api/me` + `/api/providers` report the effective selection); unlocked, a personal selection wins once set and the team value is only the default. Quotas apply in both modes (admin-role users exempt): `weeklyTokens` per user or `quotaDefaultTokens` host default, windows are UTC Monday 00:00, `0` = unlimited, and `handleLlm` returns `429 {error:"weekly quota reached", quota}` in `block` mode or adds `x-open-bot-quota: warn` (streaming + JSON) in `warn` mode. Overlay secrets never leave the server: `redactTeamConfig` (`team.ts`) nulls `apiKey`/`gatewayToken`/`sttApiKey`/`ttsApiKey` in every response and adds a per-section `secrets` map (`{hasKey, hasGatewayToken?}`). Overlay saves merge per field (`saveTeamConfig`): a present field sets it (`""`/`null` clears), an omitted field keeps the stored value — so the admin UI's blank secret inputs never wipe a saved key. Team-mode writes are gated for non-admins: image/video/model3d `PUT`/`DELETE` and watchdog-config `DELETE` are shared surfaces and answer `403 {error:"team_locked"}` outright; voice and watchdog-config `PUT` accept partial bodies with only the per-user fields (`{tts:{voice}, language}` / `{enabled, stopOnHigh}` — absent fields keep the stored config via `applyVoicePatch`/`applyWatchdogPatch`) and reject any body that also carries shared fields with the same `403`; admins always write. Admin routes (admin-session auth, `handleAdmin` in `apps/control/src/admin.ts`, fan-out via `applyTeamChange` in `apps/control/src/team-apply.ts` which re-syncs image/video/model3d/system1/watchdog/chat auth per desktop, never aborting on a down desktop — misses re-sync at boot): `GET /api/admin/team` → `{config, secrets, catalog, keys}` (redacted), `PUT /api/admin/team` (Partial<TeamConfig>; `providers` merges per field) → `{config, secrets}` (redacted), `PUT /api/admin/team/keys` (`{slug, ...fields}`; blank fields keep the stored value — shared keys are replaced, not cleared) → `{keys}`, `POST /api/admin/team/import` (copies the admin's user_keys + provider rows into the shared config and flips mode to `team`) → `{config, secrets, keys}`, `GET /api/admin/team/quotas` → `{default, behavior, users}`, `PUT /api/admin/team/quota` (`{userId, weeklyTokens}`) → `{ok, weeklyTokens}`. Migration 0013 + control/web changed → existing desktops need `bun run images && bun run update`; deploy is control+web only (no image content change).
